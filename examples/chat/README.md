# Chat without a ledger

This example is a terminal chat built on FSC, with no blockchain at all. One
FSC node is the chat server. Every user runs a chat client, which is an FSC
node too, with a terminal interface built on
[Bubble Tea](https://github.com/charmbracelet/bubbletea). Users join channels,
post to them, and send each other direct messages.

The example shows FSC as a framework for peer-to-peer applications in general.
The whole chat is a handful of small views, and none of them handles
networking, encryption or authentication. FSC gives every node an
identity issued by its organization, and every session tells the receiving
view which node is on the other end. The server never has to trust a name
inside a message, and a node without an identity from the network cannot talk
to anyone.

For the programming model itself, read the
[Programming model guide][programming-model] first.

[programming-model]: ../../docs/platform/view/programming-model.md

## The nodes

| FSC node  | Organization | Role                                                  |
| --------- | ------------ | ----------------------------------------------------- |
| `server`  | `org1`       | keeps the channels and passes channel messages on     |
| `alice`   | `org1`       | chat client                                           |
| `bob`     | `org1`       | chat client                                           |
| `charlie` | `org2`       | chat client                                           |
| `dave`    | `org2`       | chat client                                           |

The network is generated by nwo from [`topology.go`](topology.go). Each
organization has its own certificate authority, and
`fsc.WithOrganization` places each node in its organization. The server is in
`org1` only because every node needs an organization; it gives `org1` no
advantage.

Channels named after an organization, `org1` and `org2`, admit only that
organization's members. Every other channel is open to every user; the server
creates it when the first user joins.

## Talking to the server

Every operation a client asks the server for (log in, log out, list who is
online, join, leave, post) is one [`Request`](protocol.go): the client opens a
session to the server, sends the request and waits for a `Reply`. The view
that does this is `Call` in [`client.go`](client.go); its responder on the
server is `Server` in [`server.go`](server.go).

The request carries no user name. The server reads the caller from the
session, `Info().Caller`, which is the identity the transport authenticated,
and looks up that identity in its endpoint resolvers to get the node's name and
the domain of its organization (`whoIs` in `server.go`). A message from a node
that the server has no resolver for never reaches the view.

The channel rules live in [`rooms.go`](rooms.go): who is online, who is in which
channel, and who may join an organization's channel. They are plain Go with a
single lock, and [`rooms_test.go`](rooms_test.go) tests them without a network.

## Channel messages

A post goes to the server, which checks that the sender is a member and then
delivers the message to every other member at once, one short session each
(`post` and `Push` in `server.go`). The `From` of the message is the name the
server took from the session. If a member's node is down or does not answer
within ten seconds, the others still get the message on time and the sender is
told who was missed.

On the client, `Deliver` receives the message and puts it in the inbox. It is
registered with `OnlyFrom(server)`, a responder authorizer that refuses any
node other than the server before the view runs, so another client cannot fake
a channel message.

## Direct messages

A direct message goes from one client to the other without the server: `DM`
opens a session to the other user's node, and `ReceiveDM` takes the sender's
name from the session caller, never from the message. A direct message reaches
a user whose node is running, even if the user is not logged in to the server.

## What the server can and cannot do

The server sees every channel message and is trusted for the sender of a
channel message: a malicious server could misreport who posted. It never sees
direct messages. It cannot let a node into the chat that has no identity from
one of the organizations, and it cannot pose as another client in a direct
message.

## Running the example by hand

Run these commands from the `examples` directory. They need Go and this
source tree, and no Docker or Fabric binaries.

1. Generate the configuration and the crypto material:

   ```bash
   go run ./chat/cmd/network generate -p /tmp/chat-net
   ```

2. Build the server and the client:

   ```bash
   go build -o chat-server ./chat/cmd/server
   go build -o chat-client ./chat/cmd/client
   ```

3. Start the server in one terminal:

   ```bash
   FSCNODE_CFG_PATH=/tmp/chat-net/fsc/nodes/server.0 ./chat-server node start
   ```

4. Start a client per user, each in a terminal of its own:

   ```bash
   FSCNODE_CFG_PATH=/tmp/chat-net/fsc/nodes/alice.0 ./chat-client tui
   FSCNODE_CFG_PATH=/tmp/chat-net/fsc/nodes/charlie.0 ./chat-client tui
   ```

   The client writes its logs to `client.log` in its node directory.

In the client, type a line to post it to the current channel, or a command:

| Command               | Does                                                   |
| --------------------- | ------------------------------------------------------ |
| `/join <channel>`     | join a channel and make it the current one             |
| `/leave [channel]`    | leave a channel, the current one if none is given      |
| `/msg <user> <text>`  | send a direct message                                  |
| `/who`                | list the users online and their organizations          |
| `/quit` or `Ctrl-C`   | log out and exit                                       |

Try `/join org1` as `charlie` to see the server refuse it.

## Running the tests

[`chat_test.go`](chat_test.go) runs the same views without the terminal
interface: everyone logs in, posts reach the other members of a channel,
`charlie` cannot join `org1`, a non-member cannot post, direct messages arrive
with the right sender, and a post still reaches the other members when one
member's node hangs or is down. Run it with:

```bash
make integration-tests-examples-chat
```
