# Releasing

This guide is for maintainers. It lists the steps to cut a minor release of
Fabric Smart Client (FSC), seven steps and about two hours, most of it waiting
for CI, or a patch release, and how fixes reach a release branch.

## How FSC is released

- A minor `vX.Y.0` is cut from `main`, which develops the next minor. There are
  no pre-releases.
- A patch `vX.Y.Z` is cut from the _release branch_ `release-X.Y`, which starts
  at the `vX.Y.0` tag when the first fix for that minor needs a backport, and
  not before. A patch carries fixes and dependency updates only: no feature,
  breaking change, schema step or wire format change. Nodes upgrade to it one at
  a time, from any release of the same minor.
- A fix merges to `main` first. A release branch takes only backports,
  cherry-picks of fixes merged to `main`; see [Backports](#backports).
- The latest two minors are supported and take backports, security fixes
  included. When a new minor ships, the oldest leaves support. The release of a
  minor updates the backport rules and labels to match; see
  [Backports](#backports).
- A release tags the root module and every submodule (`integration`,
  `platform/fabric/services/state/cc/query`,
  `platform/view/services/comm/host/libp2p`) with the same version: `v0.28.0`,
  `integration/v0.28.0`, and so on. `scripts/tag-release.sh` finds the modules
  in the commit it tags. The submodules `replace` the root module with a
  relative path, so no `go.mod` changes before tagging. The tags are
  lightweight.
- A _release PR_, titled `build(release): vX.Y.Z`, adds everything the release
  records, so the tag contains it. These are the _release files_:
  - `docs/upgrade/releases/vX.Y.Z.json`, the _release data_, and
    `docs/upgrade/releases/vX.Y.Z.md`, the _release notes_, which become the
    body of the GitHub release. `scripts/release` generates both; what each
    holds is in [the release data README](../upgrade/releases/README.md).
  - For a minor, the storage fixtures in
    `platform/fabric/services/db/driver/sql/testdata/vX.Y.0/`, generated by
    `testdata/generate.sh --local`; see
    [the fixture README](../../platform/fabric/services/db/driver/sql/testdata/README.md).
    The fixture tests open every release directory there, so the PR changes no
    code. A patch changes no schema, so it has no fixtures.
  - For a minor, `.mergify.yml`, the backport rules of the two supported minors,
    which `scripts/release mergify` generates from the release data in the tree.
    A patch leaves it.
- The release PR starts from a commit of `main`, or of `release-X.Y` for a
  patch, its _base commit_. It is squash-merged, so it lands on that branch as
  one commit, `build(release): vX.Y.Z (#n)`, the _release commit_. The release
  commit is what gets tagged. A patch's release files stay on its release branch
  and its tag; `main` does not get them.
- The upgrade guide `docs/upgrade/vX.Y-to-vX.Z.md` (for `v0.29.0`,
  `v0.28-to-v0.29.md`) is the only part of a minor written by hand; the release
  notes link to it. A patch has no upgrade guide: its notes say that it has no
  breaking changes.

> [!CAUTION]
> The Go module proxy keeps the first content it sees for a version.
> Never move, delete or re-push a tag after pushing it; if a release is broken,
> cut the next version.

Three `make` targets cut a release: `make release-prepare`, `make release-pr`
and `make release-publish`. `scripts/release.sh` holds their logic. Every step
stops at the first error and asks before it changes anything outside your
checkout, so you can stop at any point;
[Stopping or abandoning a release](#stopping-or-abandoning-a-release) says what
to do then.

## Before you start

You need:

- write access to the repository (see [MAINTAINERS.md](../../MAINTAINERS.md)),
- `gh` logged in (`gh auth login`), Go, and Docker running: the storage fixtures
  run Postgres,
- commit signing set up (see [Signing](signing.md)),
- the git remote `upstream` pointing to
  `https://github.com/hyperledger-labs/fabric-smart-client.git`. The steps push
  to it and tag through it; release tags exist only there. If you work from a
  fork, add the remote as [Fork and clone](development.md#fork-and-clone) shows.
  If your clone's `origin` is the main repository, set `REMOTE=origin` instead.

The steps run in your current checkout. It must be clean, and
`make release-prepare` switches it to the branch `release/v0.29.0`. A separate
clone or worktree keeps your own work out of the way.

The examples release `v0.29.0` after `v0.28.0`.

## Cutting a release

These are the steps of a minor;
[Cutting a patch release](#cutting-a-patch-release) lists what differs for a
patch.

1. **Check that the upgrade guide is complete.**
   `docs/upgrade/v0.28-to-v0.29.md` describes what changes for operators and
   developers since `v0.28.0`; PRs that break something add to it as they merge.
   Every breaking change needs a section that says what to do, the opening
   paragraphs say whether organizations upgrade together, and the checklist
   lists every step. To list the breaking commits:

   ```bash
   git fetch upstream --tags
   git log --format='%h %s' v0.28.0..upstream/main | grep -E '^[0-9a-f]+ [a-z]+(\([^)]*\))?!:'
   ```

   Fix gaps in a PR and merge it first. If the guide does not exist, add it the
   same way: `make release-prepare` refuses a release without one.

2. **Run the mixed-version suite on `main`.** The release PR adds only release
   files, so the code it releases is the head of `main` it starts from. The
   `Mixed versions` workflow runs nodes of `v0.28.0` next to nodes of that code:

   ```bash
   gh workflow run mixedversion.yml -R hyperledger-labs/fabric-smart-client --ref main
   gh run watch -R hyperledger-labs/fabric-smart-client "$(gh run list -R hyperledger-labs/fabric-smart-client \
     --workflow mixedversion.yml --limit 1 --json databaseId --jq '.[0].databaseId')"
   ```

   In the run's log, every spec must have passed and none skipped. If it fails,
   do not release: fix `main` first.

3. **Prepare the release.**

   ```bash
   make release-prepare
   ```

   It picks the next minor after the latest tag (`VERSION=v0.29.0` overrides
   it). It checks that `upstream/main` has the upgrade guide and that no release
   PR of another version is open, asks you to confirm that the guide it names is
   complete, and then whether to start. On the branch `release/v0.29.0`, reset
   to `upstream/main`, it generates the release files, runs `check` and the
   fixture tests, and stages the release files.

   Read the release notes in `docs/upgrade/releases/v0.29.0.md`; after step 4
   the release PR's **Files changed** tab shows them rendered. If it stops, or
   to prepare again, see
   [Stopping or abandoning a release](#stopping-or-abandoning-a-release).

4. **Open the release PR.**

   ```bash
   make release-pr
   ```

   It commits the staged release files, signed off and signed, as
   `build(release): v0.29.0`, pushes the branch to `upstream`, and opens the
   release PR, or updates it if it is open. It refuses any other staged or
   changed file. The PR-title check labels the PR `skip-changelog`, so it stays
   out of the next changelog.

   CI gates the release. `Tests` runs the full suite on the release PR,
   including the fixture tests on the new fixture. `Release check` fails when
   the release data, the backport rules or the release notes differ from what
   `make release-prepare` generates for the PR's base commit.

5. **Get the PR reviewed and merge it.** Another maintainer approves it. `main`
   accepts only a PR that is up to date with it, so a merge to `main` while the
   release PR is open forces an update.

   > [!WARNING]
   > Do not use **Update branch** then: run `make release-prepare`
   > and `make release-pr` again, which rebuild the release on the new `main`
   > and update the same PR. If you update the branch anyway and the merged PR
   > had a changelog entry, `Release check` fails because the release notes miss
   > it.

6. **Publish the release.** `Tests` runs again on the release commit once it
   lands on `main`, which takes about an hour, and `make release-publish`
   refuses to tag before it passed. Wait for it, then run:

   ```bash
   make release-publish
   ```

   It finds the release commit of `v0.29.0` on `upstream/main`, however far
   `main` has moved since; if the release was prepared again after the merge, it
   takes the newest one. It checks the release data and the release notes
   against that commit, checks that `Tests` passed on it, lists the tags and
   asks before it pushes them. The push is all or none. For a minor, it then
   syncs the backport labels with `.mergify.yml`, asking first: it creates
   `backport/0.29` and deletes every other `backport/` label, so with `v0.31.0`
   it deletes `backport/0.29`. Last, it creates the GitHub release from the
   release notes.

   Your checkout is left on the release commit, detached. Return and delete the
   local release branch, which the merge already deleted on GitHub:

   ```bash
   git switch main
   git branch -D release/v0.29.0
   ```

   If the push fails, no tag exists and you can run the step again. If it stops
   after the push, run it again: it creates the missing GitHub release. For a
   patch published after a newer minor, set `VERSION`, for example
   `make release-publish VERSION=v0.29.1`. For anything else, see
   [Stopping or abandoning a release](#stopping-or-abandoning-a-release).

7. **Announce the release** in
   [#fabric-smart-client](https://discord.com/channels/905194001349627914/945691888348967012)
   on the LFDT Discord with a link to the GitHub release.

## Cutting a patch release

A patch `v0.29.1` follows the same steps as a minor, on the release branch
`release-0.29`:

- Land its backports on `release-0.29` first; see [Backports](#backports). Each
  must be merged: the release starts from the head of the branch.
- There is no upgrade guide to check and no mixed-version run (steps 1 and 2): a
  patch changes no schema step or wire format, and `scripts/release data`
  refuses one whose schema steps or component ranges differ from those of
  `v0.29.0`.
- `make release-prepare VERSION=v0.29.1` starts `release/v0.29.1` from
  `upstream/release-0.29`. It refuses a commit since the previous release,
  `v0.29.0` here and `v0.29.1` for `v0.29.2`, whose title is a `feat` or has a
  `!`, or whose body has a `BREAKING CHANGE:` footer, and lists the commits the
  patch carries. It writes no fixtures and needs no Docker. A patch follows the
  previous one and never skips a number.
- The release steps and CI run from the release branch, so
  `make release-prepare` refuses a branch whose `Makefile` has no `release-pr`
  target or whose `tests.yml` does not run on `release-*`: a minor cut before
  patch releases existed gets no patches.
- `make release-pr` opens the release PR against `release-0.29`, and CI runs
  there as on `main`.
- `make release-publish` finds the release commit on `release-0.29`. If a minor
  and a patch are both merged and untagged, it asks for `VERSION`. The GitHub
  release of a patch is not marked as the latest release, since a newer minor
  may be out. A patch changes no backport rule or label.
- The changelog lists the PRs merged to `release-0.29` since the previous
  release, the backports, and the notes say "No breaking changes".

One release PR can be open at a time, a minor's or a patch's.

## Backports

A fix reaches a supported minor as a _backport_: a cherry-pick of its squash
commit onto `release-X.Y`, merged there through a PR of its own.

**Rules and labels.** Mergify reads the backport rules from `.mergify.yml` on
`main`, one per supported minor. The rules and the labels come with the release
of a minor, with nothing to do by hand: its release PR brings the rules, and
`make release-publish` creates the minor's label `backport/X.Y` and deletes the
label of the minor that left support. A rule and its label exist from the
release of their minor on, before the release branch. The branch of a minor that
left support stays, so its tags stay reachable.

**Asking for one.** A fix qualifies if it repairs a bug, a security issue or a
dependency of a supported minor, and changes no API, schema step or wire format.
The PR to `main` says, under "Backport", which release branch needs it and why
the next minor is not soon enough. A maintainer who agrees adds the label
`backport/X.Y` to the PR, before or after the merge, once `release-X.Y` exists
(Mergify fails a backport to a branch that does not exist). Mergify acts on it
once the PR is merged. Adding the label to the PR is the one label step done by
hand.

**What Mergify does.** When a PR with the label merges to `main`, Mergify
cherry-picks its commit onto `release-X.Y` and opens a PR titled
`<title of #n> (backport #n)`, assigned to the original author. The PR-title
check reads the type from the title as usual. On a conflict, Mergify commits the
conflict markers, labels the PR `conflicts`, and the author resolves them on the
PR's branch. Mergify never merges: the backport PR needs CI and one maintainer's
approval, like any other PR.

**By hand**, when Mergify cannot, for example for a PR merged before its release
branch existed:

```bash
git fetch upstream
git switch -c backport-2601-0.29 upstream/release-0.29
git cherry-pick -x -s <squash commit of #2601>
git push upstream backport-2601-0.29   # or your fork
gh pr create -R hyperledger-labs/fabric-smart-client --base release-0.29 \
  --title "<title of #2601> (backport #2601)"
```

The title is the one Mergify gives. On a PR to a release branch, the `pr-title`
check accepts it for a single commit whose header is the cherry-picked
`<title of #2601> (#2601)`.

### Creating a release branch

The first backport to a minor creates its release branch, from the minor's tag.
Only a minor cut with patch releases gets one: `v0.29.0` and later. The release
steps and the workflows run from the branch, and the tree of an older tag has
neither.

Before the first release branch, a repository admin protects them once, with a
branch ruleset on `release-*` like the one on `main`: pull requests only, one
approval, squash merges, DCO. Without it, a push to a release branch skips the
CI that `make release-publish` relies on.

```bash
git fetch upstream --tags
git push upstream 'v0.29.0^{commit}:refs/heads/release-0.29'
```

Its rule and its label `backport/0.29` exist since the release of `v0.29.0`.
Backport by hand the fixes merged before the branch existed.

## Trying a release first

`DRY_RUN=1` runs every step without writing to GitHub:

```bash
make release-prepare DRY_RUN=1
make release-pr DRY_RUN=1
make release-publish DRY_RUN=1
```

- `make release-prepare` does everything it does without the setting, since it
  changes only your checkout: it resets the branch, generates the release files
  and stages them.
- `make release-pr` lists what it would commit and prints the push and the PR it
  would open. It commits nothing.
- On the release branch, `make release-publish` checks the release as if the
  branch were merged: it regenerates the release notes for the base commit and
  prints the GitHub release it would create. It lists the tags only once the
  release commit exists, that is after a real `make release-pr`; with only
  staged files it says that tagging needs the release commit. It cannot check
  `Tests`, which needs the merged PR.
- Off the release branch, after the merge, `make release-publish` runs every
  real check, `Tests` included, and prints the push and the GitHub release
  instead of making them. It is a safe check before the real step 6.

The dry run calls GitHub only to read: the changelog and the open PRs. It leaves
the branch and the staged release files of `make release-prepare`. Run
`make release-pr` without `DRY_RUN` to go on, or remove them as
[Stopping or abandoning a release](#stopping-or-abandoning-a-release) shows.

## Stopping or abandoning a release

You can stop at any point: answer `n` at a question or press Ctrl-C. The scripts
create nothing on GitHub before `make release-pr` and no tag before you confirm
the push in `make release-publish`. Temporary files are removed when a script
exits. A Ctrl-C while `make release-prepare` generates the fixtures can leave
the Postgres container it started running:

```bash
docker ps --filter ancestor=fsc.itests/postgres:latest   # the container, with a random name
docker rm -f <container>
```

What to do depends on how far the release got. The commands are for `v0.29.0`;
run them in the checkout you released from. For a patch, read its release
branch, `release-0.29` for `v0.29.1`, wherever they say `upstream/main` or
`--base main`.

**After `make release-prepare`.** The release exists only on your machine: the
branch `release/v0.29.0` and the staged release files. If `make release-prepare`
stopped partway, you are on that branch with some of the release files written
but not staged; the same commands clean up. Remove the release files, then run
`make release-prepare` again to prepare again, or switch back and delete the
branch to abandon the release:

```bash
git rm -r -f -q --cached --ignore-unmatch docs/upgrade/releases/v0.29.0.json \
  docs/upgrade/releases/v0.29.0.md platform/fabric/services/db/driver/sql/testdata/v0.29.0
rm -rf docs/upgrade/releases/v0.29.0.json docs/upgrade/releases/v0.29.0.md \
  platform/fabric/services/db/driver/sql/testdata/v0.29.0
git restore --staged --worktree .mergify.yml
git switch main                  # to abandon the release
git branch -D release/v0.29.0
```

These commands touch only the release files, staged or not, and put back the
backport rules.

> [!CAUTION]
> Do not use `git reset --hard` unless the tree holds nothing else
> you want to keep.

**After `make release-pr`, before the merge.** The release PR is open and its
branch is on `upstream`. To fix the release, change what is wrong on `main` in a
normal PR and run `make release-prepare` and `make release-pr` again: they
rebuild the branch, force-push it and update the same PR. To abandon the
release, close the PR; `--delete-branch` deletes the branch both locally and on
`upstream`:

```bash
git switch main
gh pr close release/v0.29.0 -R hyperledger-labs/fabric-smart-client --delete-branch \
  --comment "Abandoned; the next release is prepared again from main."
```

**After the merge, before `make release-publish` pushes the tags.** The release
files are on `main`, but nothing is tagged, so nothing is released. If
`make release-publish` stops on a check, fix the cause and run it again, or
prepare the release again: `make release-prepare` and `make release-pr` give a
PR that updates the release files on `main`. To abandon the release, revert
every release commit of the version in a PR, so that the untagged release data
leaves `main`. There are two if the release was prepared again after the merge:

```bash
git switch -c revert/v0.29.0 upstream/main
git revert --no-edit -s -S $(git log --format=%H --grep='^build(release): v0\.29\.0\( (#[0-9]*)\)\?$' upstream/main -- \
  docs/upgrade/releases/v0.29.0.json docs/upgrade/releases/v0.29.0.md)
git push upstream revert/v0.29.0
gh pr create -R hyperledger-labs/fabric-smart-client --base main --head revert/v0.29.0 \
  --title 'Revert "build(release): v0.29.0"'
```

The revert also removes the release's fixtures. Until it merges,
`make release-publish` keeps finding `v0.29.0`, and `make release-prepare`
prepares `v0.29.0` again, since the next version follows the latest tag.

**After the tags are pushed.** The release exists: the Go module proxy may
already have fetched it, and it keeps that content for good. Never delete or
move the tags. If the GitHub release is missing, run `make release-publish`
again. If the release is broken, say so in the GitHub release and on Discord,
fix it on `main`, and cut the next version.

## Releasing from a fork

The same steps cut a release in your fork, to test the process or a change to it
end to end. `RELEASE_REPO` names the fork; the branch, the release PR, the tags
and the GitHub release are then the fork's, and the release notes link to the
fork. `REMOTE` defaults to `origin`, which must point to the fork.

```bash
export RELEASE_REPO=<you>/fabric-smart-client
make release-prepare VERSION=v0.29.0
make release-pr
# review and squash-merge the PR in the fork
make release-publish
```

- Set `VERSION`. The next minor is computed from the tags in your local
  repository, and those can differ from the main repository's.
- Merge the release PR with **Squash and merge**, which the main repository
  enforces and `make release-publish` relies on: it looks for the commit
  `build(release): v0.29.0 (#n)`.
- `Tests` must pass on the release commit in the fork before
  `make release-publish` tags, so the fork needs Actions enabled. The full suite
  takes about an hour of the fork's Actions minutes.
- The release tags are only in the main repository, so the steps fetch its tags
  and its `main`. The previous release comes from those tags, and the changelog
  is generated in the main repository: it lists the PRs merged there up to the
  latest commit of its `main` that the fork's release is based on. The fork's
  own commits are not in it.
- `Release check` skips the release notes in a fork: the token of the fork's CI
  cannot generate notes in the main repository. `make release-publish` checks
  them from your machine.
- `make release-publish` pushes the tags to the fork and then removes them from
  your local repository, so a later release of the main repository in the same
  checkout does not see them. Go never sees the fork's tags: `go get` of the
  module resolves it in the main repository.

Each step checks that `REMOTE` points to `RELEASE_REPO`, so a release meant for
the main repository never goes to a fork, and a fork's release never goes to the
main repository.

## Settings

The steps take these settings, all optional, as environment variables or on the
`make` command line:

| Setting        | Meaning                                                                                                                                       | Default                                     |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| `VERSION`      | the version `make release-prepare` prepares, `vX.Y.0` or a patch `vX.Y.Z`; `make release-publish` takes it when several releases are untagged | the next minor after the latest release tag |
| `DRY_RUN=1`    | do every local step and check, and print what would be written to GitHub; see [Trying a release first](#trying-a-release-first)               | off                                         |
| `RELEASE_REPO` | the repository to release in, `owner/name`; see [Releasing from a fork](#releasing-from-a-fork)                                               | `hyperledger-labs/fabric-smart-client`      |
| `REMOTE`       | the git remote of `RELEASE_REPO`                                                                                                              | `upstream`, or `origin` for a fork          |
| `YES=1`        | answer every question with yes, including the tag push of `make release-publish`                                                              | off                                         |

## Without the scripts

The steps by hand, for when a script stops and you cannot fix the cause:

1. **The release PR.** In a clean worktree of `upstream/main`, generate the
   release files and commit them, nothing else. The scratch files go to a
   temporary directory.

   ```bash
   git fetch upstream --tags
   git worktree add -b release/v0.29.0 ../fsc-release upstream/main
   cd ../fsc-release
   tmp=$(mktemp -d)
   go run ./scripts/release/refnode version --json > "$tmp/report.json"
   go run ./scripts/release data --version v0.29.0 --report "$tmp/report.json" \
     > docs/upgrade/releases/v0.29.0.json
   gh api repos/hyperledger-labs/fabric-smart-client/releases/generate-notes \
     -f tag_name=v0.29.0 -f previous_tag_name=v0.28.0 -f target_commitish="$(git rev-parse HEAD)" \
     --jq .body > "$tmp/changelog.md"
   go run ./scripts/release notes --data docs/upgrade/releases/v0.29.0.json \
     --changelog "$tmp/changelog.md" > docs/upgrade/releases/v0.29.0.md
   go run ./scripts/release mergify > .mergify.yml
   go run ./scripts/release check --report "$tmp/report.json"
   platform/fabric/services/db/driver/sql/testdata/generate.sh --local v0.29.0
   go test -run Fixtures ./platform/fabric/services/db/driver/sql/
   git add docs/upgrade/releases/v0.29.0.* platform/fabric/services/db/driver/sql/testdata/v0.29.0 \
     .mergify.yml
   git commit -s -S -m "build(release): v0.29.0"
   git push upstream release/v0.29.0
   gh pr create -R hyperledger-labs/fabric-smart-client --base main --head release/v0.29.0 \
     --title "build(release): v0.29.0"
   ```

2. **The tags**, on the release commit, not a later head of `main`: the release
   notes and the fixtures describe it. Check that `Tests` passed on it first.
   The dry run lists one tag per module; `PUSH=upstream` creates the tags and
   pushes exactly these, all or none. `make tag-release` takes `DRY=1`, not
   `DRY_RUN=1`. It refuses a version that is not `vMAJOR.MINOR.PATCH`, a tag
   that exists, and a commit without the release data.

   ```bash
   git fetch upstream
   commit=$(gh pr view <release PR number> -R hyperledger-labs/fabric-smart-client \
     --json mergeCommit --jq .mergeCommit.oid)
   gh run list -R hyperledger-labs/fabric-smart-client --workflow tests.yml --event push --commit "$commit"
   git checkout "$commit"
   make tag-release VERSION=v0.29.0 DRY=1
   make tag-release VERSION=v0.29.0 PUSH=upstream
   ```

3. **The GitHub release**, with the release notes as its body, and for a minor
   the backport label of each rule in `.mergify.yml`; delete every other
   `backport/` label:

   ```bash
   gh release create v0.29.0 -R hyperledger-labs/fabric-smart-client --verify-tag \
     --title v0.29.0 --notes-file docs/upgrade/releases/v0.29.0.md
   gh label create backport/0.29 -R hyperledger-labs/fabric-smart-client \
     --description "Backport to release-0.29 once merged to main"
   ```

Remove the worktree with `cd .. && git worktree remove fsc-release`.
