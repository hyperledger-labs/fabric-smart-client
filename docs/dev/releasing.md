# Releasing

This guide is for maintainers. It lists the steps to cut a release of Fabric Smart Client
(FSC).

## How FSC is released

- Every release is a minor cut from `main`. There are no pre-releases, release branches or
  backports.
- A release tags the root module and every submodule (`integration`,
  `platform/fabric/services/state/cc/query`, `platform/view/services/comm/host/libp2p`) with
  the same version: `v0.28.0`, `integration/v0.28.0`, and so on. `scripts/tag-release.sh`
  finds the modules in the commit it tags. The submodules `replace` the root module with a
  relative path, so no `go.mod` changes before tagging. The tags are lightweight.
- A release PR `build(release): vX.Y.Z` adds everything the release records, so the tag
  contains it:
  - `docs/upgrade/releases/vX.Y.Z.json`, the release data, and `docs/upgrade/releases/vX.Y.Z.md`,
    the body of the GitHub release, generated by `scripts/release`. What each file holds is in
    [the release data README](../upgrade/releases/README.md).
  - The storage fixtures in `platform/fabric/services/db/driver/sql/testdata/vX.Y.Z/`, generated
    by `testdata/generate.sh --local` from the commit the PR is based on; see
    [the fixture README](../../platform/fabric/services/db/driver/sql/testdata/README.md). The
    fixture tests open every release directory there, so the PR changes no code.
- The upgrade guide `docs/upgrade/v<previous>-to-v<this>.md` is the only part of a release
  written by hand; the notes link to it.
- The Go module proxy keeps the first content it sees for a version. Never move, delete or
  re-push a tag after pushing it; if a release is broken, cut the next version.

Three `make` targets cut a release; `scripts/release.sh` holds their logic. They work from
the remote `upstream`, which must point to
`https://github.com/hyperledger-labs/fabric-smart-client.git`, not to your fork: release tags
exist only there. If you work from a fork, add the remote as [Rebasing](rebasing.md) shows.
Every step stops at the first error and asks before it changes anything outside your checkout,
so you can stop at any point and continue by hand as
[Without the scripts](#without-the-scripts) shows. To try a release first, run the steps as a
[dry run](#trying-a-release-first) or [on a fork](#releasing-from-a-fork).

The steps take these settings, all optional, as environment variables or `make` variables:

| Setting | Meaning | Default |
|---|---|---|
| `VERSION` | the version `release-prepare` prepares, `vX.Y.0` | the next minor after the main repository's latest release |
| `DRY_RUN=1` | do every local step and check, and print what would be written to GitHub | off |
| `RELEASE_REPO` | the repository to release in, `owner/name` | `hyperledger-labs/fabric-smart-client` |
| `REMOTE` | the git remote of `RELEASE_REPO` | `upstream`, or `origin` for a fork |
| `YES=1` | answer every question with yes | off |

CI is the release gate. `Tests` always runs on the release PR and on the release commit that
lands on `main`, the full suite including the fixture tests on the new fixture, and
`release-publish` tags only a commit `Tests` passed on. `Release check` fails when the data
file or the notes differ from what `release-prepare` generates for the PR's base, for example
after the PR was updated with `main`.

## Before you start

You need write access to the repository (see [MAINTAINERS.md](../../MAINTAINERS.md)), `gh`
logged in (`gh auth login`), Docker running (the storage fixtures run Postgres), commit
signing set up (see [Signing](signing.md)), and a clean checkout. The examples release
`v0.29.0` after `v0.28.0`.

## Cutting a release

1. **Check that the upgrade guide is complete.** `docs/upgrade/v0.28-to-v0.29.md` describes
   what changes for operators and developers since `v0.28.0`; PRs that break something add to
   it as they merge. Every breaking change needs a section that says what to do, the opening
   paragraphs say whether organizations upgrade together, and the checklist lists every step.
   To list the breaking commits:

   ```bash
   git fetch upstream --tags
   git log --format='%h %s' v0.28.0..upstream/main | grep -E '^[0-9a-f]+ [a-z]+(\([^)]*\))?!:'
   ```

   Fix gaps in a PR and merge it first.

   `data` writes `upgrade.mode` `stop-all` for every release; marking one `rolling` is a
   change to `scripts/release` (see [the release data README](../upgrade/releases/README.md)).

2. **Run the mixed-version suite on `main`.** The release PR adds only data and fixtures, so
   the code it releases is the head of `main` it starts from. The `Mixed versions` workflow
   runs nodes of `v0.28.0` next to nodes of that code. Start it, wait for it, and check that its
   specs ran rather than skipped:

   ```bash
   gh workflow run mixedversion.yml -R hyperledger-labs/fabric-smart-client --ref main
   ```

3. **Prepare the release.**

   ```bash
   make release-prepare
   ```

   It picks the next minor after the latest tag (`VERSION=v0.29.0` overrides it), checks that
   `upstream/main` has its upgrade guide and that no release PR of another version is open, and
   asks you to confirm that the guide it names is complete, then whether to start. On a new branch
   `release/v0.29.0` from `upstream/main` it generates the release data, the notes and the
   storage fixtures, runs `check` and the fixture tests, and stages the three outputs. Read
   the notes in `docs/upgrade/releases/v0.29.0.md` as GitHub will show them. To prepare
   again, remove the staged outputs first, as
   [Stopping or abandoning a release](#stopping-or-abandoning-a-release) shows.

4. **Open the release PR.**

   ```bash
   make release-pr
   ```

   It commits the staged files, signed off and signed, as `build(release): v0.29.0`, pushes
   the branch to `upstream` and opens the PR, or updates it if it is open. It refuses any other
   staged or changed file. The PR-title check labels the PR `skip-changelog`, so it stays out
   of the next changelog.

5. **Get the PR reviewed and merge it.** Another maintainer approves it. Merge it soon: once a
   PR with a changelog entry merges to `main`, GitHub asks to update the release PR, and the
   updated PR's notes no longer list every change, so `Release check` fails. Then run
   `make release-prepare` and `make release-pr` again.

6. **Publish the release.**

   ```bash
   make release-publish
   ```

   It finds the latest release commit of `v0.29.0` on `upstream/main`, the squash merge of the
   release PR, whatever the head of `main` is now; if the release was opened again after a
   merge, that is the later one. It checks the data and the notes against that commit and that
   `Tests` passed on it, which can take an hour after the merge, lists the tags it would create
   and asks before it pushes them, all or none.
   Then it creates the GitHub release with the notes and leaves the checkout on the release
   commit, detached; `git switch main` returns. If the push fails, no tag is left behind and
   you can run it again. If it stops after pushing the tags, run it again: it creates the
   GitHub release that is missing.

7. **Announce the release** in
   [#fabric-smart-client](https://discord.com/channels/905194001349627914/945691888348967012) on
   the LFDT Discord with a link to the GitHub release.

## Trying a release first

`DRY_RUN=1` runs every step without writing to GitHub:

```bash
make release-prepare DRY_RUN=1
make release-pr DRY_RUN=1
make release-publish DRY_RUN=1
```

`release-prepare` does everything it does without the setting, since it changes only your
checkout: it builds the branch, generates the files and stages them. `release-pr` lists what it
would commit and prints the push and the PR it would open; it commits nothing. On the release
branch, `release-publish` checks the release as if the branch were merged: it regenerates the
notes for the commit the branch starts from, and prints the tags and the GitHub release it
would create. It cannot check `Tests`, which needs the merged PR. The dry run does call GitHub
to read: the changelog and the open PRs.

A dry run leaves the branch and the staged files of `release-prepare`. Run `make release-pr`
without `DRY_RUN` to go on, or remove them as
[Stopping or abandoning a release](#stopping-or-abandoning-a-release) shows.

## Releasing from a fork

The same steps cut a release in your fork, to test the process or a change to it end to end
without touching the main repository. `RELEASE_REPO` names the fork; the branch, the PR, the
tags and the GitHub release are then the fork's, and the notes link to the fork. `REMOTE`
defaults to `origin`, which must point to the fork.

The release tags are only in the main repository, so the steps fetch its tags and its `main`.
The previous release comes from those tags, and the changelog is generated in the main
repository: it lists the PRs merged there up to the latest commit of its `main` that the
fork's release is based on. A fork's own commits are not in it.

```bash
export RELEASE_REPO=<you>/fabric-smart-client
make release-prepare VERSION=v0.29.0
make release-pr
# review and squash-merge the PR in the fork
make release-publish
```

Set `VERSION`: the fork's tags may be older than the main repository's. Merge the release PR
with **Squash and merge**, which the main repository enforces and `release-publish` relies on,
since it looks for the commit `build(release): v0.29.0 (#n)`. Before `release-publish` tags,
`Tests` must pass on that commit in the fork, so the fork needs Actions enabled; the full
suite takes about an hour of the fork's Actions minutes. `Release check` skips the notes in a
fork: the token of the fork's CI cannot generate notes in the main repository, so
`release-publish` checks them from your machine. Go never sees the fork's tags: `go get` of the
module resolves it in the main repository.

Each step checks that `REMOTE` points to `RELEASE_REPO`, so a release meant for the main
repository never goes to a fork, and a fork's release never goes to the main repository.

## Stopping or abandoning a release

You can stop at any point: answer `n` at a question or press Ctrl-C. The scripts create
nothing on GitHub before `make release-pr` and no tag before you confirm the push in
`make release-publish`. Temporary files are removed when a script exits. A Ctrl-C while
`make release-prepare` generates the fixtures can leave the Postgres container it started
running; `docker ps` shows it, and `docker rm -f <container>` removes it.

What to do depends on how far the release got. The commands are for `v0.29.0`; run them in
the checkout you released from.

**After `make release-prepare`.** The release exists only on your machine: the branch
`release/v0.29.0` and the three staged outputs. To prepare again, remove the outputs and run
`make release-prepare`, which builds the branch from `upstream/main` again. To abandon the
release, also delete the branch:

```bash
git rm -r -f -q --cached docs/upgrade/releases/v0.29.0.json docs/upgrade/releases/v0.29.0.md \
  platform/fabric/services/db/driver/sql/testdata/v0.29.0
rm -rf docs/upgrade/releases/v0.29.0.json docs/upgrade/releases/v0.29.0.md \
  platform/fabric/services/db/driver/sql/testdata/v0.29.0
git switch main                  # to abandon the release
git branch -D release/v0.29.0
```

These commands touch only the release outputs, staged or not. Do not use `git reset --hard`
unless the tree holds nothing else you want to keep.

**After `make release-pr`, before the merge.** The release PR is open and its branch is on
`upstream`. To fix the release, change what is wrong on `main` in a normal PR and run
`make release-prepare` and `make release-pr` again: they rebuild the branch, force-push it and
update the same PR. To abandon the release, close the PR and delete both branches:

```bash
gh pr close release/v0.29.0 -R hyperledger-labs/fabric-smart-client --delete-branch \
  --comment "Abandoned; the next release is prepared again from main."
git switch main
git branch -D release/v0.29.0
```

**After the merge, before `make release-publish` pushes the tags.** The release files are on
`main`, but nothing is tagged, so nothing is released. If `make release-publish` stops on a
check, fix the cause and run it again, or open the release again: `make release-prepare` and
`make release-pr` give a PR that updates the files on `main`. To abandon the release, revert
the release commit in a PR, so that the untagged data file leaves `main`:

```bash
git switch -c revert/v0.29.0 upstream/main
git revert --no-edit -s -S "$(git log --format=%H --diff-filter=A -n1 -- docs/upgrade/releases/v0.29.0.json)"
git push upstream revert/v0.29.0
gh pr create -R hyperledger-labs/fabric-smart-client --base main --head revert/v0.29.0 \
  --title 'Revert "build(release): v0.29.0"'
```

The revert also removes the release's fixtures. Until it merges, `make release-publish` keeps
finding `v0.29.0`, and `make release-prepare` prepares `v0.29.0` again, since the next version
follows the latest tag.

**After the tags are pushed.** The release exists: the Go module proxy may already have
fetched it, and it keeps that content for good. Never delete or move the tags. If the GitHub
release is missing, run `make release-publish` again. If the release is broken, say so in the
GitHub release and on Discord, fix it on `main`, and cut the next version.

## Without the scripts

The steps by hand, for when a script stops and you cannot fix the cause:

1. **The release PR.** In a clean worktree of `upstream/main`, generate the three outputs and
   commit them, nothing else: `report.json` and `changelog.md` are scratch files.

   ```bash
   git fetch upstream --tags
   git worktree add -b release/v0.29.0 ../fsc-release upstream/main
   cd ../fsc-release
   go run ./scripts/release/refnode version --json > report.json
   go run ./scripts/release data --version v0.29.0 --report report.json \
     > docs/upgrade/releases/v0.29.0.json
   gh api repos/hyperledger-labs/fabric-smart-client/releases/generate-notes \
     -f tag_name=v0.29.0 -f previous_tag_name=v0.28.0 -f target_commitish="$(git rev-parse HEAD)" \
     --jq .body > changelog.md
   go run ./scripts/release notes --data docs/upgrade/releases/v0.29.0.json \
     --changelog changelog.md > docs/upgrade/releases/v0.29.0.md
   go run ./scripts/release check --report report.json
   platform/fabric/services/db/driver/sql/testdata/generate.sh --local v0.29.0
   go test -run Fixtures ./platform/fabric/services/db/driver/sql/
   git add docs/upgrade/releases/v0.29.0.* platform/fabric/services/db/driver/sql/testdata/v0.29.0
   git commit -s -S -m "build(release): v0.29.0"
   git push upstream release/v0.29.0
   gh pr create -R hyperledger-labs/fabric-smart-client --base main --head release/v0.29.0 \
     --title "build(release): v0.29.0"
   ```

2. **The tags**, on the commit the PR merged as, not a later head of `main`: the notes and the
   fixtures describe it. Check that `Tests` passed on that commit first. The dry run lists one
   tag per module; `PUSH=upstream` creates the tags and pushes exactly these, all or none.
   `make tag-release` refuses a version that is not `vMAJOR.MINOR.PATCH`, a tag that exists,
   and for a minor a commit without `docs/upgrade/releases/v0.29.0.json`. A patch has no
   release data yet, so `make tag-release` tags it without; patch releases are otherwise not
   supported.

   ```bash
   git fetch upstream
   git checkout "$(gh pr view <release PR number> -R hyperledger-labs/fabric-smart-client \
     --json mergeCommit --jq .mergeCommit.oid)"
   make tag-release VERSION=v0.29.0 DRY=1
   make tag-release VERSION=v0.29.0 PUSH=upstream
   ```

3. **The GitHub release**, with the notes as its body:

   ```bash
   gh release create v0.29.0 -R hyperledger-labs/fabric-smart-client --verify-tag \
     --title v0.29.0 --notes-file docs/upgrade/releases/v0.29.0.md
   ```

Remove the worktree with `git worktree remove ../fsc-release`.
