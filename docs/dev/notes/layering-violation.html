Crossing the Delivery Boundary

The fix is right. It is in the wrong package. A stream reader learned to recognise Postgres deadlocks and rejected channel configurations — and the proof is one line we wrote to undo it.

Where does the retry logic live?
—

Why one retry rule cannot serve both callers

The delivery service hands blocks to two completely different kinds of code. Only one of them is safe to replay — and the shared layer cannot tell them apart.

Safe to retry

The committer feed. Committer.Commit checks vault status and skips transactions it has already committed, so replaying a block is a no-op. This is the property the whole retry rests on.

Not safe to retry

Scan callbacks. Scan, ScanBlock and ScanFromBlock run the application's function. We know nothing about it. Retrying turns a scan the caller cancelled into a full budget of waiting per block.

The line that proves it

Because the retry sits in the shared layer, it applied to both callers. So we added this to switch it back off for scans:

// platform/fabric/core/generic/delivery/service.go — inside runBlockScan
deliveryService.commitRetries = 0

A feature that has to be cancelled for half its callers is in the wrong place. Move the retry into the committer and this line has nothing left to undo — it deletes itself. That is the clean test that the move was correct.

The naming was the second clue. A field inside a supposedly committer-agnostic component is called commitRetries; the counters are commit_retries and commit_failures. None of it could be named without saying commit.

What the committer already has

This is why the logic belongs there rather than being plumbed upward: the committer holds every input a classification needs, while delivery has to import them.

Held by CommitterWhat it answers
VaultIs this storage error contention that will clear, or corruption that will not?
MembershipServiceDid a configuration transaction fail to apply, and is that fatal for this channel?
LedgerIs this a transient peer RPC failure, or a transaction the ledger says is invalid?
ChannelConfigHow many attempts, and how long between them.

It also receives the whole block. Commit(ctx, block) has strictly more information to classify with than readBlocks does.

The rework, and what survives it

This is a package move plus rewiring — a few hours, not a rename. The thinking is done and none of it is thrown away.

Moves across intact

The four classes. The escalate-on-exhaustion behaviour. The wrapped-cause handling with errors.Join. Every test. The reasoning about which errors are transient — which was the hard part.

Changes

classify and the retry loop move to committer/. The counters join the committer's Metrics, gaining a channel label. delivery.commitRetries becomes a committer setting. The workaround is deleted.

// Delivery goes back to what its own doc comment always claimed:
stop, err := d.callback(b.ctx, b.block)
// err is already final — the committer retried what was worth retrying
// classify() and the retry loop are gone from this package

One question to settle first

If the committer retries internally and returns only final errors, delivery still needs a rule for when to stop the channel. Two shapes, and it is the maintainer's call:

Option A — stop on any error

Delivery stops whenever the callback fails, full stop. The committer never returns an error it wants ignored. Simpler, and it matches "by then it is already permanent or fatal".

Option B — read a sentinel

The committer returns a typed error that delivery inspects for the stop decision. More flexible, but it puts a little committer knowledge back into delivery — the thing this move exists to remove.
