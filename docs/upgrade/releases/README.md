# Release data

Every FSC release has two files here, both generated by `scripts/release` and
never edited by hand:

- `vX.Y.Z.json`, the release data: what the release contains, in a form tooling
  can read.
- `vX.Y.Z.md`, the body of the GitHub release.

Releases cut before this directory existed have no files here.

## The release data

```json
{
  "version": "v0.29.0",
  "modules": ["integration/v0.29.0", "platform/fabric/services/state/cc/query/v0.29.0", "platform/view/services/comm/host/libp2p/v0.29.0", "v0.29.0"],
  "upgrade": {"mode": "stop-all", "guide": "docs/upgrade/v0.28-to-v0.29.md"},
  "stores": [{"type": "vault", "dialect": "postgres", "steps": [{"version": 1, "name": "create tables", "hash": "…", "contract": false}]}],
  "components": [{"name": "view", "min": 1, "max": 1}],
  "dropped_next": [],
  "tested_with": {"fabric": "3.1.4", "fabric_x_committer": "1.0.7", "fabric_x_tools": "v1.0.3", "go": "1.27.3", "postgres": "16.2"}
}
```

- `modules`: the tags the release creates, one per module.
- `upgrade`: how a deployment upgrades to the release. `stop-all` means every
  node of a network stops before any node runs the release. `rolling` means
  organizations upgrade their nodes one at a time while the network runs, as
  [Rolling upgrades](../rolling-upgrade.md) describes. `data` writes `stop-all`
  for every minor; a minor becomes `rolling` through a change to
  `scripts/release`, once the mixed-version suite has run against its previous
  release. A patch is `rolling`: `data` refuses one whose `stores` or
  `components` differ from those of the release before it. `guide` is the
  upgrade guide of a minor, and empty for a patch.
- `stores` and `components`: the schema steps of every FSC store and the wire
  format ranges, from `node version --json` of the reference binary
  `scripts/release/refnode` (see
  [the Node CLI reference](../../reference/node-cli.md#version)). A step with
  `contract: true` makes a rollback past it a restore from backup; see
  [schema migrations](../../platform/view/services/schema-migrations.md).
- `dropped_next`: the versions the next minor stops supporting. It is empty
  until FSC declares them.
- `tested_with`: the versions the release's tests ran against: Go from `go.mod`,
  the others from the `FABRIC_VERSION`, `FABRIC_X_COMMITTER_VERSION`,
  `FABRIC_X_TOOLS_VERSION` and `POSTGRES_VERSION` pins in the `Makefile`
  (`postgres` without the image suffix).

The field names are fixed: fields are added, never renamed or removed. The
output is deterministic, so the file of a release can be regenerated and
compared.

## The release notes

The notes say only what is not written down elsewhere, and link to the rest:

- **Upgrading:** for a minor, a link to the upgrade guide on `main`, which says
  what an upgrade requires. A fix to the guide after the release reaches every
  reader. A minor without a guide is refused; see
  [Upgrade guides](../../dev/documentation.md#upgrade-guides). A patch has no
  guide; its notes say that it has no breaking changes.
- **Tested with:** the versions in `tested_with`, as one row.
- A link to the release data file at the release tag, which lists every store's
  schema steps and the component version ranges. A released record never
  changes, so the tag is where it lives.
- The changelog GitHub generates from the PR titles, grouped by label,
  unchanged.

The guide and the data file are linked rather than quoted, so the release body
keeps no second copy of either. The data link works once the tag is pushed,
since the release PR commits the file before tagging.

## Previewing a release

`make release-prepare` generates both files;
[Without the scripts](../../dev/releasing.md#without-the-scripts) lists the
commands it runs, to preview a release by hand. It needs the remote `upstream`
that [Before you start](../../dev/releasing.md#before-you-start) describes.

`check` fails when a data file here was edited by hand: a file whose release is
tagged must equal the file at the tag, since a released record never changes,
and a file without a tag must equal what `data` generates from the checked-out
tree. An untagged file also fails when the tree changed after it was generated,
by a schema step, a component range or a pin; regenerate it. `check` also fails
when `.mergify.yml` is not what `mergify` generates: the backport rules of the
two highest minors with a data file here, from `v0.29.0` on, the first minor
that can get a release branch. `check` does not read the notes, since the
changelog they include comes from GitHub: the `Release check` workflow and
`make release-publish` regenerate them with the changelog GitHub generates for
the release PR's base commit, and fail when they differ. Review them in the
release PR.

A patch `vX.Y.Z` follows `vX.Y.(Z-1)`, and a minor `vX.Y.0` follows
`vX.(Y-1).0`: `data` refuses a version whose predecessor has no tag, and the
changelog starts from that predecessor. The files of a patch are on its release
branch `release-X.Y` and at its tag, not on `main`, so `check` on `main` skips
the patch's tag.
