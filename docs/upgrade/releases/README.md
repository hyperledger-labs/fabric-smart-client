# Release data

Every FSC release has two files here, both generated by `scripts/release` and never edited by
hand:

- `vX.Y.Z.json`, the release data: what the release contains, in a form tooling can read.
- `vX.Y.Z.md`, the body of the GitHub release.

Releases cut before this directory existed have no files here.

## The release data

```json
{
  "version": "v0.29.0",
  "modules": ["integration/v0.29.0", "platform/fabric/services/state/cc/query/v0.29.0", "platform/view/services/comm/host/libp2p/v0.29.0", "v0.29.0"],
  "upgrade": {"mode": "stop-all", "guide": "docs/upgrade/v0.28-to-v0.29.md"},
  "stores": [{"type": "vault", "dialect": "postgres", "steps": [{"version": 1, "name": "create tables", "hash": "…", "contract": false}]}],
  "components": [{"name": "view", "min": 1, "max": 1}],
  "dropped_next": [],
  "tested_with": {"fabric": "3.1.4", "fabric_x_committer": "1.0.7", "fabric_x_tools": "v1.0.3", "go": "1.27.3", "postgres": "16.2"}
}
```

- `modules`: the tags the release creates, one per module.
- `upgrade`: how a deployment upgrades to the release. `stop-all` means every node of a network
  stops before any node runs the release. `guide` is the upgrade guide of the release.
- `stores` and `components`: the schema steps of every FSC store and the wire format ranges,
  from `node version --json` of the reference binary `scripts/release/refnode` (see
  [the Node CLI reference](../../reference/node-cli.md#version)). A step with `contract: true`
  makes a rollback past it a restore from backup; see
  [schema migrations](../../platform/view/services/schema-migrations.md).
- `dropped_next`: the versions the next minor stops supporting. It is empty until FSC declares
  them.
- `tested_with`: the versions the release's tests ran against: Go from `go.mod`, the others
  from the `FABRIC_VERSION`, `FABRIC_X_COMMITTER_VERSION`, `FABRIC_X_TOOLS_VERSION` and
  `POSTGRES_VERSION` pins in the `Makefile` (`postgres` without the image suffix).

The field names are fixed: fields are added, never renamed or removed. The output is
deterministic, so the file of a release can be regenerated and compared.

## The release notes

The notes say only what is not written down elsewhere, and link to the rest:

- **Upgrading:** a link to the upgrade guide on `main`, which says what an upgrade requires. A
  fix to the guide after the release reaches every reader. A minor without a guide is refused;
  see [Upgrade guides](../../dev/documentation.md#upgrade-guides).
- **Tested with:** the versions in `tested_with`, as one row.
- A link to the release data file at the release tag, which lists every store's schema steps
  and the component version ranges. A released record never changes, so the tag is where it
  lives.
- The changelog GitHub generates from the PR titles, grouped by label, unchanged.

The guide and the data file are linked rather than quoted, so the release body keeps no second
copy of either. The data link works once the tag is pushed, since the release PR commits the
file before tagging.

## Previewing a release

From the repository root, with the release tags fetched (`git fetch upstream --tags`, where
`upstream` points to the main repository; see [Releasing](../../dev/releasing.md#before-you-start)):

```sh
go run ./scripts/release/refnode version --json > report.json
go run ./scripts/release bump                                   # the next minor, e.g. v0.29.0
go run ./scripts/release data --version v0.29.0 --report report.json > docs/upgrade/releases/v0.29.0.json
gh api repos/hyperledger-labs/fabric-smart-client/releases/generate-notes \
  -f tag_name=v0.29.0 -f previous_tag_name=v0.28.0 -f target_commitish=main --jq .body > changelog.md
go run ./scripts/release notes --data docs/upgrade/releases/v0.29.0.json --changelog changelog.md > docs/upgrade/releases/v0.29.0.md
go run ./scripts/release check --report report.json
```

`check` fails when a data file here was edited by hand: a file whose release is tagged must
equal the file at the tag, since a released record never changes, and a file without a tag
must equal what `data` generates from the checked-out tree. An untagged file also fails when
the tree changed after it was generated, by a schema step, a component range or a pin;
regenerate it. The notes are not checked, since
the changelog they include comes from GitHub; review them in the release PR.

`data` refuses a patch version (`vX.Y.Z` with `Z` above 0): a patch has no upgrade guide of its
own, so only minors have release data.
