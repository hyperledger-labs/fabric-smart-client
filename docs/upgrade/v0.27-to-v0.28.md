# Upgrading from v0.27 to v0.28

This guide takes an application built on Fabric Smart Client (FSC) v0.27.0 to v0.28.0. Coming from an older release, first follow [v0.26-to-v0.27.md](v0.26-to-v0.27.md).

The recipient exchange changes on the wire: every organization that exchanges recipient identities
must upgrade together (see [Recipient exchange](#recipient-exchange)).

Every change below applies to both the Fabric and the Fabric-x platform, except where a section
names the Fabric committer or says it runs on Fabric only: the txID check under
[Endorser](#endorser), the committer's handling of store conflicts under
[Write-once stores](#write-once-stores), and [Forged envelopes in a block](#forged-envelopes-in-a-block).
The [Fabric-x API](#fabric-x-api) changes apply to Fabric-x only.

# For operators

## Storage

**Applies to:** Every node.

- Every FSC store records its schema version in `<prefix>_schema_versions`, which the first start creates. The node therefore needs the right to create a table, unless it uses `skipCreateTable: true` together with `node migrate`.
- On first start every store runs step 1. On a database written by v0.27 it creates the versions table, checks the existing tables and records version 1; it takes an exclusive lock only on a table it has to convert. On an older database it converts the vault and KVS layout as v0.27 did, which can take long on a large Postgres vault. Back up first.
- While a store migrates after the listeners have started, such as a channel's vault, `/readyz` answers 503 with reason `migrating`; `/healthz` stays 200.
- With `skipCreateTable: true` an FSC store with pending steps fails to open with `schema migration pending` instead of opening unprepared. Run `node migrate` before starting such a node. `node migrate --check` lists every pending step and exits 10; 11 means a store is newer than the binary, 1 that it could not check, 2 invalid arguments.
- Every open records the node's `fsc.id` and the binary's highest step in `<prefix>_schema_openers`. A node that runs with `skipCreateTable: true` needs `SELECT`, `INSERT` and `UPDATE` on that table; without them every store fails to open and the node does not start.
- A waiting Postgres migrator logs the session that holds the migration lock. Set `application_name` in each node's `dataSource` to its pod name, so the log names the pod. `fsc.storage.migrationLockTimeout` makes it fail after a time; by default it waits.
- `node migrate` fails if a store would use memory because it names no persistence and `fsc.persistences.default` is not defined.
- A binary refuses a store whose `readable_by` is above the highest step it knows; only contract steps raise it, and none of the FSC stores has one. v0.27 binaries do not read the versions table and keep working against a v0.28 database. A later release's binary can be rolled back until one of its contract steps has run. v0.27 binaries leave no row in `<prefix>_schema_openers`, so upgrade every v0.27 node to v0.28 or later before a later release runs a contract step.
- On Postgres, use one role that runs migrations and owns the tables and one node role with DML, read access to the versions table, and `SELECT`, `INSERT` and `UPDATE` on the openers table.

See [Schema migrations](../platform/view/services/schema-migrations.md) and [`node migrate`](../reference/node-cli.md#node-migrate).

- New, off by default: `queryTimeout` in a persistence's `opts` bounds how long a statement, or a batch commit, may run, so a database that stops answering no longer stalls the node silently. Choose a value above the slowest batch commit. A value without a unit, such as `30`, fails startup. See [Query timeout](../configuration.md#query-timeout).
- The Fabric committer retries a block that fails with `SQLITE_BUSY` on SQLite, or with SQLSTATE `55P03` (`lock_timeout`) or `57014` (`statement_timeout`) on Postgres, within `committer.retries`. Before, it degraded the channel on the first such failure.

## Endorser

A node validates a transaction it receives from a remote peer before signing, endorsing, or
storing it, so that peer cannot present a creator that disagrees with its proposal or, on Fabric,
pick the txID the transaction is stored under; see [Security Model](../platform/view/security-model.md#data-received-from-peers).
A transaction that fails this check is refused and never reaches the committer. A valid peer's
transaction can now be refused for reasons that were previously silent or caught later:

- This node has not loaded the channel configuration yet, such as at startup or during catch-up.
  The receive call returns a retryable error to the calling view, which decides whether to try
  again; nothing retries automatically. This case is not counted as a rejection.
- This node has loaded the channel configuration, but it lags behind the sender's: for example, an
  organization was added to the channel and this node does not know its MSP yet. The transaction
  is refused and counted as `invalid_tx`. Check `fsc_connection_state{component="delivery"}` for
  that channel; a connection stuck in `reconnecting` or `connecting` means the node is not
  receiving blocks and its MSP configuration is stale.
- The creator's certificate expired or was revoked. The transaction is refused with no retry.
- The peer built the transaction with `fabric.WithTxID` and a txID that is not
  `ComputeTxID(nonce, creator)`. Fabric peers already reject such a transaction at validation; this
  node now also refuses it before endorsing or storing it, on the Fabric platform. FSC skips this
  check on Fabric-x, because the Fabric-x committer does not require
  `txid == ComputeTxID(nonce, creator)` for data transactions. On Fabric-x a remote peer can
  therefore still choose the txID its transaction is stored under; the proposal header
  consistency checks and the creator check still apply.

## Recipient exchange

The recipient views of `platform/fabric/services/state` (`RequestRecipientIdentity`,
`ExchangeRecipientIdentities` and their responders) send a proof of ownership with every recipient
identity and refuse an identity without a valid one; see
[Security Model](../platform/view/security-model.md#recipient-proof-of-ownership). `RecipientData`
is JSON, so a v0.27 node ignores the new `Proof` field, but a v0.28 node refuses the unproven
identities a v0.27 node sends:

| Initiator / responder | `RequestRecipientIdentity` | `ExchangeRecipientIdentities` |
|---|---|---|
| old → new | works (old initiator ignores the proof) | fails: new responder refuses the old initiator's unproven identity; the old initiator gets `received error from remote [recipient proof: missing]` |
| new → old | fails: new initiator refuses the unproven reply and returns `recipient proof: missing`; the `recipient_proof` warn line gives reason `missing` | fails the same way |

This is a coordinated upgrade. Every organization whose nodes exchange recipient identities with
each other upgrades in the same window. There is no compatibility mode, because accepting a
missing proof would leave the attack open: an attacker would just omit the proof. Each refusal is
counted as `recipient_proof`.

How a receiver verifies the identities it receives:

- x509 recipient identities need no extra configuration and no channel; verifying one shows the
  sender holds its key, not that it belongs to an MSP.
- A receiver verifies an idemix recipient identity whose MSP is an idemix MSP of a channel
  through that channel's MSPs: the channel set with `state.WithChannel` on
  `ExchangeRecipientIdentities` and its responder, otherwise the network's default channel. Its
  credential must be valid for that MSP; the receiver needs no idemix credential of its own. Such
  an exchange needs that channel known and its configuration in force: on a network with no
  default channel, pass `state.WithChannel`. A node still catching up refuses the identity with an
  error wrapping `driver.ErrNotInitialized`, and a node that refused the channel configuration it
  received with one wrapping `driver.ErrConfigRejected`; the first clears on retry once the
  configuration arrives. When the node that cannot verify is the responder, the initiator only gets
  `received error from remote [recipient verification unavailable: channel not ready]`, which
  wraps no error type. Neither is counted as a rejection.
- An idemix identity whose MSP is not an idemix MSP of that channel is verified through the
  node's local idemix MSPs, as in v0.27, but only under the local MSP's own MSP ID.
- An x509 identity verifies only if its public key is an ECDSA key; any other key is refused with
  reason `no verifier`.
- Each node's `fsc.identity.cert.file` must be the certificate its peers list for it under
  `fsc.endpoint.resolvers`. Formatting differences, such as line endings or PEM headers, do not
  matter.

## Write-once stores

**Applies to:** Every node.

The envelope, endorsed-transaction and audit-info stores reject a write that differs from the record
already stored under the same key, and keep the stored record; see
[Security Model](../platform/view/security-model.md#write-once-stores). Writing the same record again
still succeeds.

- An endorsement whose transaction differs from the one this node already endorsed under that txID
  fails, and the initiator receives an error.
- The Fabric committer discards a valid transaction whose envelope differs from the one stored
  under its txID, with a validation message containing `store conflict`, and keeps committing the
  rest of the block.
- Both are counted as `store_conflict`.

## Binding store

The binding store maps identities that remote parties send, such as recipient identities, to the
long-term identity of their owner. It refuses to store a known long-term identity (one with a
resolver or a self-row) as another identity's ephemeral, keeps the existing row when an unproven
bind conflicts with it, and lets a bind made after a proof of ownership replace it; see
[Security Model](../platform/view/security-model.md#identity-bindings). Refused and conflicting binds
log a warning and are counted, and do not fail the caller, so startup and application flows are
unchanged.

- A node whose own MSP identity is listed in a Fabric network's `endpoint.resolvers` under a name
  other than its `fsc.id` has that identity registered as a separate resolver, so binding it to the
  node's view identity is refused. The node starts, logs a `binding_refused` warning, and the MSP
  identity is not resolved to the node. Give the entry the node's `fsc.id` as its name, or remove it.
- A remote node that rotated its certificate leaves alias rows pointing at its old certificate.
  The alias binds at startup report `binding_conflict` and the rows are kept. An alias still
  resolves to the resolver it names, because the endpoint service looks up aliases before the
  binding store.

Bindings stored by an earlier release were not checked. A row that binds a long-term identity to
another party redirects that identity, and every new bind to it, to that party. Binds after the
upgrade do not repair such a row: `BindProven` replaces the binding of the proven ephemeral, and
leaves a row on the long-term identity itself in place. Find these rows once, as described below.
In the default store the table is `fsc_default_bind` (see
[Database layout](../platform/view/services/database-layout.md)). The `ephemeral_hash` of an
identity is `base64(sha256(identity bytes))`.

A row found this way is a candidate, and many candidates are legitimate. A node binds its own
identities to each other: its Fabric MSP identity to its FSC identity, and the identity of an
`endpoint.resolvers` entry to the FSC identity of the resolver with the same name. Such a row
binds one identity of a node to another identity of the same node, and endorsement checks rely on
it (`IsBoundTo`); deleting it breaks them. A candidate is planted only if `bound_to` belongs to a
different node than `long_term`. To tell, decode both identities and compare the
certificates they carry. Both columns hold the identity bytes: a PEM certificate for an FSC
identity, and for a Fabric identity a serialized `SerializedIdentity` that holds the MSP ID
followed by a PEM certificate. Extract the PEM block and run `openssl x509 -noout -subject
-issuer` on it. Two identities belong to the same node if they are the node's own FSC and MSP
identities, or the identities of resolver entries with the same name in its configuration. Delete
a row only if its two identities are clearly owned by different parties. An identity that carries
no certificate, such as an Idemix identity, cannot be attributed this way; keep such rows.

On Postgres, this query lists the candidates among identities that are the target of some row,
with the identities as text:

```sql
SELECT b.ephemeral_hash,
       encode(b.long_term_id, 'escape') AS bound_to,
       encode(l.long_term_id, 'escape') AS long_term
FROM fsc_default_bind b
JOIN (SELECT DISTINCT long_term_id FROM fsc_default_bind) l
  ON b.ephemeral_hash = encode(sha256(l.long_term_id), 'base64')
WHERE b.long_term_id <> l.long_term_id;
```

SQLite has no SHA-256 function, so hash the long-term identities outside SQL:

```bash
DB=path/to/fsc.sqlite; T=fsc_default_bind
sqlite3 "$DB" "SELECT DISTINCT hex(long_term_id) FROM $T" | while read -r lt; do
  h=$(printf '%s' "$lt" | xxd -r -p | openssl dgst -sha256 -binary | base64)
  sqlite3 "$DB" "SELECT ephemeral_hash, CAST(long_term_id AS TEXT), CAST(X'$lt' AS TEXT) FROM $T WHERE ephemeral_hash = '$h' AND long_term_id <> X'$lt'"
done
```

A long-term identity that was redirected before it was ever bound is the target of no row, so also
look up the identity of each configured resolver with
`SELECT long_term_id FROM fsc_default_bind WHERE ephemeral_hash = '<hash>'`, and judge a row that
names another identity as above:

- For an `fsc.endpoint.resolvers` entry, the hash is
  `openssl x509 -in <identity.path> | openssl dgst -sha256 -binary | base64`.
- For a Fabric `endpoint.resolvers` entry, the identity is the serialized MSP identity, with the
  certificate as the MSP sanitizes it, which `openssl` cannot reproduce. Start the node with the
  logging spec `fsc.platform.fabric.core.generic.endpoint=debug` and read the hash from the line
  `Resolver [<name>,<domain>][<addresses>] <hash>` it logs for each entry.

Delete planted rows while the node is stopped.

## Forged envelopes in a block

**Applies to:** Fabric networks.

A block can carry an invalid envelope of any header type that someone forged with an honest
transaction's txID and had ordered ahead of it, followed by the honest `VALID` envelope. The
committer, which also does not store the invalid envelope, remote finality checks
(`delivery.DeliverReceive`), transaction scans (`Delivery.Scan`, `ScanFromBlock`) and the
delivery-based listener manager take the verdict of the txID's `VALID` envelope if the block has
one. Such a transaction is reported as committed where a forgery could make it look invalid.
Nothing needs to be configured; see
[Security Model](../platform/view/security-model.md#write-once-stores).

Block scans (`Delivery.ScanBlock`, `ScanBlockFrom`) still hand over whole blocks. A callback that
resolves txIDs from a block must call `committer.ShadowedEnvelopes` itself.

## TLS listener certificates

**Applies to:** Nodes whose gRPC, web or metrics listener uses TLS.

New: `reloadInterval` in `fsc.tls` and in the `tls` block of `fsc.grpc`, `fsc.web` and
`fsc.metrics` makes a listener re-read its certificate and key files at that interval and serve a
renewed certificate from the next handshake on, without a restart; see
[configuration](../configuration.md). It is off when absent or 0, so an existing `core.yaml`
behaves as before. A value below `1s`, or one written without a unit such as `30`, fails startup.
The websocket P2P listener does not reload and refuses the key.

New: `fsc_tls_cert_not_after{listener}` exports each listener's certificate expiry in Unix seconds,
with `listener` one of `grpc`, `web` and, when it has its own address, `metrics`; see
[Listener TLS](../platform/view/services/monitoring_metrics.md#listener-tls).

## P2P

**Applies to:** Every node.

New: `fsc.p2p.maxResponders` bounds the responders a node runs concurrently across all peers, and
separately the rejections pending across all peers. It defaults to 0, unlimited, so an existing
`core.yaml` behaves as before. When set, a first message from a peer under
`fsc.p2p.maxRespondersPerPeer` that would exceed it gets the error reply
`node_busy: too many concurrent responders on this node`, counted as
`fsc_view_services_view_p2p_rejections{reason="node_busy"}`; a peer at its own limit still gets
`busy`. Once as many rejections are pending across all peers, further first messages are dropped
and their initiators wait for their session to time out. See
[comm](../platform/view/services/comm/readme.md).

New: a responder an application registers with an authorizer answers a refused node with
`unauthorized: caller may not start this view`, and a failed check with
`authorizer_error: authorizer failed`, counted under those reasons in
`fsc_view_services_view_p2p_rejections`. Nothing changes for responders registered without one.

- Every stream opens with a preamble that carries the node's FSC version, framing epoch and
  version ranges; see [Stream preamble](../platform/view/services/comm/readme.md#stream-preamble).
  Nodes of v0.27 and v0.28 still connect over both transports, so a network upgrades node by node.
- WebSocket: a v0.28 node logs, once per peer, `peer [<id>] sent no preamble` for each v0.27 peer.
  The message is informational.
- libp2p: v0.28 nodes speak `/fsc/view/2.0.0` with each other and `/fsc/view/1.0.0` with v0.27
  nodes. The libp2p host module (`platform/view/services/comm/host/libp2p`) is tagged together with
  the root module; update both.
- New: `node peers --check` dials every configured websocket peer, reads its preamble and
  exits 11 if a peer's framing epoch or ranges do not match this binary's; `node version --json`
  prints the binary's ranges and every store's steps. See
  [Node CLI](../reference/node-cli.md#node-peers---check).
- `fscnode.New()` no longer panics when no `core.yaml` is found: `version` runs, `node migrate` and
  `node peers --check` exit 1 with the missing-file error, and `node start` fails with it like any
  other start error. A `core.yaml` that exists but does not parse still makes `New()` panic.
- A v0.28 initiator states, on each message of a session it opened, the version of each component's
  formats it chose for the session, and, for a view that declares one, its protocol name. A v0.27
  node ignores both. A responder that gets a version outside its range answers
  `no_common_version: <component> <version> not in [<min>, <max>]`, counted as
  `fsc_view_services_view_p2p_rejections{reason="no_common_version"}`; between v0.27 and v0.28
  nodes every version is 1, so this does not happen during the upgrade.

## libp2p

**Applies to:** Nodes with `fsc.p2p.type: libp2p`.

- A libp2p node runs no DHT and needs no bootstrap node: it dials each peer at the `P2P` address
  of the peer's resolver entry. It starts while any other node is down.
- `fsc.p2p.opts.libp2p.bootstrapNode` is ignored. A node that has it set logs a warning at start;
  remove the key.
- Give every resolver entry of a party the node opens sessions to a `P2P` address. A node without
  one fails with `no addresses`, unless a connection from that peer is open; a v0.27 node may have
  reached such a peer only because the peer was connected to it as its bootstrap node.
- A v0.27 node still connects to its bootstrap node at start and fails to start if it is down. Keep
  the bootstrap node running until every node runs v0.28, then remove it. A v0.27 node that
  bootstraps from a v0.28 node starts, and logs `error while announcing` once.
- libp2p listens and dials on TCP only. A `listenAddress` of another transport, such as
  `/udp/.../quic-v1`, fails at start.

## Remote view API

**Applies to:** Nodes that serve the remote view API.

New: `fsc.view.remote.maxConcurrentRequests` bounds the commands the remote view API runs at once,
across every backend. It defaults to 0, unlimited, so an existing `core.yaml` behaves as before.
When set, a command over the bound gets gRPC `Unavailable`
`node is busy: too many concurrent view requests` (HTTP `503`, WebSocket close `1013`), the same
code a draining node returns, and is counted as
`fsc_view_services_view_grpc_server_requests_rejected{reason="busy"}`. The command did not run, so
the client may send it again. An idle stream keeps its slot until the client closes it. See
[configuration](../configuration.md).

## Monitoring

New: `fsc_view_services_security_rejections{kind}` counts inputs from remote peers
rejected by a security check: `invalid_tx` by the endorser, `binding_refused` and
`binding_conflict` by the endpoint service, `recipient_proof` by the recipient views,
`unauthorized` by the P2P service for a node a responder's authorizer refused, and `store_conflict`
by the endorser and the committer; see
[Security metrics](../platform/view/services/monitoring_metrics.md#security).

New: `fsc_view_services_view_grpc_server_requests_rejected` has the reason `denied`, for a command an
application policy checker refused; see [View Service metrics](../platform/view/services/monitoring_metrics.md#view-service).

New: `fsc_view_services_comm_host_websocket_ws_rejected_streams{reason}` and
`fsc_view_services_comm_host_libp2p_rejected_streams{reason}` count streams refused because of the
peer's preamble, with reason `version`; see [Metrics](../platform/view/services/monitoring_metrics.md).

# For developers

## Storage

- FSC stores implement `migrate.Versioned`. `CreateSchema()` on them still creates the tables without recording a version.
- `postgres.PrimaryKey` and `sqlite.PrimaryKeyColumns` accept any value with `QueryRowContext`, including `*sql.Conn`. `ReorderPrimaryKeyTx` runs the reorder inside a transaction the caller holds.
- An SDK whose stores `node migrate` should reach provides a `viewsdk.StoreOpenerEntry` into the dig group `fsc-store-openers` during `Install` (see [DB drivers](../platform/view/services/db-driver.md#reaching-stores-from-node-migrate)).
- `migratetest.CheckSteps` checks an application store's steps against a golden file of `Step.Hash` values, so a released step cannot change unnoticed.
- An application store that calls `migrate.CreateSchema` itself passes the options from the persistence's `ConfigProvider.MigrateOptions`, so it records its opener and honors the lock timeout.
- The storage fixtures under `platform/fabric/services/db/driver/sql/testdata/` hold databases written by v0.26.0 and v0.27.0, which the tests migrate at every change.
- Breaking: the store constructors of `platform/view/services/storage/driver/sql/common` (`NewKeyValueStore`, `NewBindingStore`, `NewSignerInfoStore`, `NewAuditInfoStore`, `NewSimpleKeyDataStore`) and of `platform/fabric/services/db/driver/sql/common` (`NewVaultStore`, `NewMetadataStore`, `NewEnvelopeStore`, `NewEndorseTxStore`) take a trailing `common.QueryTimeout`. Pass `0` for no deadline. `RWDB` has a `QueryTimeout` field, which `NewPersistenceWithOpts` sets from the persistence's `queryTimeout`.

## View API

- New: `viewsdk.PolicyCheckerEntry` (`platform/view/sdk/dig`) adds a `server.PolicyChecker` to the
  remote view API, run after the built-in signature and client check, and `view.ErrDenied` for its
  refusals (see [Remote View API Access Control](../platform/view/services/view-service.md#remote-view-api-access-control)).
  Nothing changes for an application that registers none.
- An application that decorates the `server.PolicyChecker` binding now receives the SDK's
  composite checker instead of the `*server.AccessControlChecker`. With no group checker it runs the
  same check. A decorator that type-asserts its argument to `*server.AccessControlChecker` must
  instead keep it as a `server.PolicyChecker`, or move its check into a `PolicyCheckerEntry`.
- The view SDK provides `*server.AccessControlChecker` under its own type, so an SDK that provides
  that type itself fails `Install` with a duplicate; decorate it instead.

## Responder authorization and typed rejections

- New: `RegisterResponderWithOptions(responder, initiatedBy, opts...)` on `view.Registry` and
  `view.Manager`, with `view.WithIdentity` and `view.WithAuthorizer`. A `view.ResponderAuthorizer`
  (or `view.AuthorizerFunc`) decides which authenticated nodes may start the responder; it refuses
  with an error wrapping `view.ErrDenied`. See
  [Authorizing responders](../platform/view/programming-model.md#authorizing-responders).
  `RegisterResponder`, `RegisterResponderWithIdentity` and `RegisterResponderFactory` are unchanged.
- The registry keeps the responder instance and its identity per initiator. A responder type
  registered for two initiators with different instances or identities runs, for each, as registered
  for that initiator, where it ran as the latest registration for either. `GetResponder` returns the
  latest registration for the initiator, where it returned the first instance of that responder type.
  An application that registers several instances for one initiator, such as one per TMS, gets the
  last one from both P2P dispatch and `GetResponder`. `GetView` likewise returns the latest view
  registered with an empty initiator, where it returned the first.
- `p2p.ViewManager` (`platform/view/services/view/p2p`) has `ResponderForCaller(protocol, caller)`
  in place of `ExistResponderForCaller`; `view.Manager` implements both. A custom implementation of
  `p2p.ViewManager` must add it, and look the responder up by protocol name first, then by caller.
- New: `session.RejectionError` and the sentinels `session.ErrRejected`, `ErrUnknownView`, `ErrBusy`,
  `ErrDraining` and `ErrUnauthorized` (`platform/view/services/comm/session`). The session receive
  helpers return them for a node's error reply, so `errors.Is` tells a busy node from an unknown
  view. The error text is unchanged. `ReadFirstMessageOrPanic` panics with that error instead of
  its text. See [comm](../platform/view/services/comm/readme.md#error-replies-a-node-sends-unasked).

## Fabric API

- New: `endorser.ValidateReceived(tx)`, `endorser.NewTransactionFromPeer(ctx, peer, raw)` and `endorser.ErrInvalidTransaction`
  (`platform/fabric/services/endorser`), for code that builds a `*fabric.Transaction` from bytes
  outside `endorser.NewTransactionFromBytes` or `endorseView` and wants the same check. It decides
  from the network of `tx` whether to run the txID check.
- New: `security.Rejections`, `security.GetRejections`, and the `security.Kind` constants
  (`platform/view/services/security`), registered in the view SDK. Existing code does not need to
  change; the endorser, the endpoint service, the recipient views, the P2P service and the
  committer report to it.
- New: `committer.ShadowedEnvelopes(block)` (`platform/fabric/core/generic/committer`) tells which
  invalid envelopes of a block, of any header type, a valid endorser transaction with the same
  txID shadows; see
  [Forged envelopes in a block](#forged-envelopes-in-a-block). A custom
  `events.EventInfoMapper` is not called for a shadowed envelope.

## Recipient exchange API

- Breaking on the wire: the recipient views require a proof of ownership, see
  [Recipient exchange](#recipient-exchange). Their Go signatures are unchanged.
- New: `state.RecipientData.Proof`, and `state.SignRecipientProof`, `state.VerifyRecipientProof`,
  `state.ProofContext`, the `state.Tag*` constants and `state.ErrRecipientProof`
  (`platform/fabric/services/state/proof.go`), for applications with their own recipient
  exchange. An idemix signature over the proof payload links the pseudonym to the signer's node for
  anyone who sees it.
- A preset `Identity` on `RespondRequestRecipientIdentityView` must have a signer in the network's
  signature service. Otherwise the view fails with `failed getting signer for recipient identity
  [...]` and sends no reply.
- New: `fabric.SignerService.GetVerifier(id)`, which returns the network's verifier for a Fabric
  identity. It is not a membership check: an x509 identity is not validated against any MSP.
- New: `fabric.SignerService.LookupVerifier(id)` and `sig.Service.LookupVerifier(id)`, which
  return a verifier without caching one they have to deserialize, for identities chosen by a
  remote party.
- New: `fabric.MSPManager.IsIdemixMSP(mspID)`.
- An idemix MSP provider (`platform/fabric/core/generic/msp/idemix`) deserializes an identity
  only if its `SerializedIdentity.Mspid` equals the provider's MSP ID; it fails with `expected MSP
  ID [...]` otherwise. A deserializer built from an issuer key alone (`idemix.NewDeserializer`)
  has no MSP ID and accepts any.
- New: a `Channel` field on `ExchangeRecipientIdentitiesView` and
  `RespondExchangeRecipientIdentitiesView`, set from `state.WithChannel` by
  `ExchangeRecipientIdentities` and `RespondExchangeRecipientIdentities`. It selects the channel
  that verifies idemix recipients; see [Recipient exchange](#recipient-exchange).
- New: `id.CanonicalIdentity(raw)` (`platform/view/services/id`), the canonical PEM form of a
  certificate identity, which `id.LoadIdentity` also returns.

## Storage API

- Breaking: `PutEnvelope`, `PutEndorseTx` and `PutAuditInfo` (`platform/common/driver`), and through
  them `fabric.Vault.StoreEnvelope`, `fabric.Vault.StoreTransaction` and
  `sig.Service.RegisterAuditInfo`, return an error wrapping `driver.ErrConflict`
  (`platform/view/services/storage/driver`) when a different record is already stored under the
  key; they returned nil and kept the stored record. Writing the stored record again still returns
  nil. Callers that write a record under a key they do not own should handle `ErrConflict`.
- A custom store implementing these interfaces must follow the same rule.
  `common.SimpleKeyDataStore.PutDataStrict` (`platform/view/services/storage/driver/sql/common`)
  implements it for a key-data table.
- `PutMetadata` keeps the first value and returns nil, unchanged.

## Binding store API

- Breaking for custom binding stores: `driver.BindingStore` (`platform/common/driver`) has a new
  method, `ReplaceBinding(ctx, longTerm, ephemeral) error`. It binds `ephemeral` to `longTerm`,
  replacing an existing binding, and must refuse an `ephemeral` that has a self-row with an error
  wrapping `driver.ErrBindingRefused` (`platform/view/services/storage/driver`). A custom store
  should also refuse such ephemerals in `PutBindings` the same way; the SQL stores do.
- New: `endpoint.Service.BindProven(ctx, longTerm, ephemeral)`, for binds made after verifying a
  proof of ownership, and `endpoint.Service.SetRejections`, which the view SDK calls.
- `endpoint.Service.Bind` keeps its signature and return values. Callers that bind
  counterparty-chosen identities, such as a Panurus `Request.BindTo` or an htlc flow, keep
  working: a bind that conflicts with an existing row returns nil and keeps that row, so the
  identity stays resolved to its first owner.

## libp2p API

- Removed: `P2PHost.Lookup` and `P2PHost.Wait` (`platform/view/services/comm/host`),
  `P2PNode.Lookup` (`platform/view/services/comm`) and `ServiceDiscovery.LookupAll`
  (`platform/view/services/comm/host/websocket/routing`). A custom `P2PHost` or
  `ServiceDiscovery` drops these methods.
- `libp2p.NewHostGeneratorProvider` (`platform/view/services/comm/host/libp2p`) takes no endpoint
  service: `NewHostGeneratorProvider(config, metricsProvider)`.
- nwo: removed `Topology.SetBootstrapNode`, `Node.SetBootstrap`, the `Bootstrap` field of
  `node.Node` and `node.Peer`, `Platform.BootstrapNode`, `Platform.BootstrapViewNodeGroupRunner`
  and `Platform.FSCNodeGroupRunner` (`integration/nwo/fsc`), and `Network.BootstrapNode`
  (`integration/nwo/fabric/network`). A topology drops its `SetBootstrapNode` call and the node it
  added only to be the bootstrap node. `Platform.Members` starts every node in parallel.
- `go-libp2p-kad-dht` is no longer a dependency, so GO-2024-3218 no longer applies.

## Fabric-x API

- `queryservice.NewRemoteQueryService` takes a client factory
  `func(skip string) (committerpb.QueryServiceClient, string, error)`. `skip` is empty on the first
  attempt; on the retry after `Unavailable` it is the endpoint that failed, and the factory should
  return a client for another endpoint if one exists.
- `queryservice.GRPCClientProvider.QueryServiceClient` and `config.ClientProvider.QueryServiceClient`
  take a second argument `skip`, the target to avoid; pass `""` to skip nothing. Regenerate
  counterfeiter mocks of `GRPCClientProvider`.

## Protocol names and format versions

- New: `view.WithProtocol(component, name)` and `view.ProtocolView`. An initiator view that
  implements `Protocol() (component, name string)` opens its sessions under that name, and a
  responder registered with `WithProtocol` for it answers them whatever the initiator's Go type
  path. Responders are still found by type path, so nothing changes for an application that adds
  neither. To give a protocol a stable name, add the method to the initiator and the option to
  its responder registration, in the same release:
  `RegisterResponderWithOptions(&Responder{}, &Initiator{}, view.WithProtocol("iou", "create"))`.
  The type path keeps working for peers of the previous release; the initiator type may move once
  every peer runs the release with the name. See
  [Protocol names](../platform/view/programming-model.md#protocol-names).
- New: `preamble.RegisterComponent(name, min, max)` (`platform/view/services/comm/preamble`)
  registers an application component with the range of versions of its formats the binary
  supports; call it when the SDK is built or in `main`. A name registered twice, including one of
  FSC's (`view`, `fabric`, `fabricx`), panics. `view.VersionedSession`, `view.SessionVersion` and
  `view.ErrNoCommonVersion` (`platform/view/view`) return the version a session uses, and
  `session.RejectionError` maps a `no_common_version` rejection to `view.ErrNoCommonVersion`. See
  [Versions of a protocol's formats](../platform/view/programming-model.md#versions-of-a-protocols-formats).
- `view.Message` has the fields `Protocol` and `Versions`. A struct literal without field names
  no longer compiles.

## Integration test harness (`nwo`)

- `integration/nwo` and its `fsc`, `fabric` and `fabricx` packages do not link the libp2p host. A
  project that runs its topologies on websocket only drops libp2p from its build and needs no
  `replace` for `platform/view/services/comm/host/libp2p`.
- `(*fsc.Topology).AddSDKForCommType` is removed. A topology that runs on websocket only calls
  `topology.AddSDK(base)`. A topology that can run on libp2p sets `P2PCommunicationType` as
  before and calls `topology.AddSDKWithExtensions(base, &libp2psupport.SDK{})`
  (`integration/nwo/fsc/support/libp2p`), which serves websocket nodes as well.

# Checklist

Operators:

- Add `fsc_view_services_security_rejections` to dashboards, and alert if `invalid_tx`
  rises steadily rather than in an isolated burst, which can indicate a misbehaving or malicious
  peer.
- To bound the load many peers together put on a node, set `fsc.p2p.maxResponders`, and watch
  `fsc_view_services_view_p2p_rejections{reason="node_busy"}`.
- To bound the commands view API clients run at once, set `fsc.view.remote.maxConcurrentRequests`,
  and watch `fsc_view_services_view_grpc_server_requests_rejected{reason="busy"}`.
- If a transaction a peer builds with `fabric.WithTxID` starts being refused, confirm the peer
  passes a txID equal to `ComputeTxID(nonce, creator)`.
- Alert on any `binding_refused` and on a steady `binding_conflict` rate.
- Alert on any `store_conflict`.
- Run the planted-binding check of [Binding store](#binding-store) once after the upgrade.
- Upgrade every organization that exchanges recipient identities in the same window. Exchanges
  of idemix recipient identities need the channel that verifies them (`state.WithChannel` or the
  network's default channel) configured on both sides. Alert on a steady `recipient_proof` rate.
- To rotate a TLS listener certificate without a restart, set `reloadInterval`, and alert on
  `fsc_tls_cert_not_after` before it is reached.
- libp2p: give every resolver entry a `P2P` address, keep the bootstrap node up until the last
  v0.27 node is upgraded, then remove it and `fsc.p2p.opts.libp2p.bootstrapNode`.

Developers:

- Add `ReplaceBinding` to any custom `driver.BindingStore` implementation.
- Add `ResponderForCaller(protocol, caller)` to any custom `p2p.ViewManager` implementation.
- Initiators whose Go type may move: implement `view.ProtocolView` and register the responder with
  `view.WithProtocol`.
- Responders that only some nodes may start: register them with `view.WithAuthorizer` instead of
  checking `Session().Info().Caller` inside the responder.
- Applications with their own recipient exchange: consider sending and checking a proof of
  ownership with `state.SignRecipientProof` / `state.VerifyRecipientProof` and binding with
  `endpoint.Service.BindProven`.
- Handle `driver.ErrConflict` from `PutEnvelope`, `PutEndorseTx`, `PutAuditInfo` and the vault and
  signature service methods built on them, and make custom implementations of those stores
  write-once.
- Decorators of the `server.PolicyChecker` binding: do not type-assert to
  `*server.AccessControlChecker`; an SDK that provides that type itself must decorate it instead
  (see [View API](#view-api)).
- Applications that register several responder instances or identities for one initiator, or rely
  on which registration `GetResponder` or `GetView` returns: check the
  [per-initiator rules](#responder-authorization-and-typed-rejections).
- Preset `Identity` on `RespondRequestRecipientIdentityView`: make sure the network's signature
  service has a signer for it.
- Idemix MSP providers: identities whose `Mspid` differs from the provider's MSP ID no longer
  deserialize through it.
- Fabric-x: pass the new `skip` argument to `QueryServiceClient`, update custom client factories of
  `queryservice.NewRemoteQueryService`, and regenerate counterfeiter mocks of `GRPCClientProvider`.
- Use field names in `view.Message` struct literals.
- Drop `Lookup` and `Wait` from custom `P2PHost` implementations and `LookupAll` from custom
  `ServiceDiscovery` implementations, the endpoint service argument of
  `libp2p.NewHostGeneratorProvider`, and nwo `SetBootstrapNode` calls with their bootstrap nodes.
- Callbacks of `Delivery.ScanBlock` or `ScanBlockFrom` that resolve txIDs from a block: skip the
  envelopes `committer.ShadowedEnvelopes` reports.
- Integration tests: replace `AddSDKForCommType(base, commType)` with `AddSDK(base)` on
  websocket only, or with `AddSDKWithExtensions(base, &libp2psupport.SDK{})` where the topology
  can run on libp2p.
