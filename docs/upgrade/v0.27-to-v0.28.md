# Upgrading from v0.27 to v0.28

This guide takes an application built on Fabric Smart Client (FSC) v0.27.0 to v0.28.0. Coming from an older release, first follow [v0.26-to-v0.27.md](v0.26-to-v0.27.md).

Every change below applies to both the Fabric and the Fabric-x platform, except the txID check
noted under [Endorser](#endorser), which runs on Fabric only.

# For operators

## Storage

**Applies to:** Every node.

- Every FSC store records its schema version in `<prefix>_schema_versions`, which the first start creates. The node therefore needs the right to create a table, unless it uses `skipCreateTable: true` together with `node migrate`.
- On first start every store runs step 1. On a database written by v0.27 it creates the versions table, checks the existing tables and records version 1; it takes an exclusive lock only on a table it has to convert. On an older database it converts the vault and KVS layout as v0.27 did, which can take long on a large Postgres vault. Back up first.
- While a store migrates after the listeners have started, such as a channel's vault, `/readyz` answers 503 with reason `migrating`; `/healthz` stays 200.
- With `skipCreateTable: true` an FSC store with pending steps fails to open with `schema migration pending` instead of opening unprepared. Run `node migrate` before starting such a node; `node migrate --check` exits non-zero while steps are pending.
- A binary refuses a store whose `readable_by` is above the highest step it knows. v0.27 binaries do not read the versions table and keep working against a v0.28 database; rolling back across a later step means restoring a backup.
- On Postgres, use one role that runs migrations and owns the tables and one node role with DML and read access to the versions table.

See [Schema migrations](../platform/view/services/schema-migrations.md) and [`node migrate`](../reference/node-cli.md#node-migrate).

## Endorser

A node validates a transaction it receives from a remote peer before signing, endorsing, or
storing it, so that peer cannot present a creator that disagrees with its proposal or, on Fabric,
pick the txID the transaction is stored under; see [Security Model](../platform/view/security-model.md#data-received-from-peers).
A transaction that fails this check is refused and never reaches the committer. A valid peer's
transaction can now be refused for reasons that were previously silent or caught later:

- This node has not loaded the channel configuration yet, such as at startup or during catch-up.
  The receive call returns a retryable error to the calling view, which decides whether to try
  again; nothing retries automatically. This case is not counted as a rejection.
- This node has loaded the channel configuration, but it lags behind the sender's: for example, an
  organization was added to the channel and this node does not know its MSP yet. The transaction
  is refused and counted as `invalid_tx`. Check `fsc_connection_state{component="delivery"}` for
  that channel; a connection stuck in `reconnecting` or `connecting` means the node is not
  receiving blocks and its MSP configuration is stale.
- The creator's certificate expired or was revoked. The transaction is refused with no retry.
- The peer built the transaction with `fabric.WithTxID` and a txID that is not
  `ComputeTxID(nonce, creator)`. Fabric peers already reject such a transaction at validation; this
  node now also refuses it before endorsing or storing it, on the Fabric platform. FSC skips this
  check on Fabric-x, because the Fabric-x committer does not require
  `txid == ComputeTxID(nonce, creator)` for data transactions. On Fabric-x a remote peer can
  therefore still choose the txID its transaction is stored under; the proposal header
  consistency checks and the creator check still apply.

## Monitoring

New: `fsc_view_services_security_rejections{kind}` counts inputs from remote peers
rejected by a security check. Currently only `kind="invalid_tx"` is reported, by the endorser; see
[Security metrics](../platform/view/services/monitoring_metrics.md#security).

# For developers

## Storage

- FSC stores implement `migrate.Versioned`. `CreateSchema()` on them still creates the tables without recording a version.
- `postgres.PrimaryKey` and `sqlite.PrimaryKeyColumns` accept any value with `QueryRowContext`, including `*sql.Conn`. `ReorderPrimaryKeyTx` runs the reorder inside a transaction the caller holds.
- An SDK whose stores `node migrate` should reach provides a `viewsdk.StoreOpenerEntry` into the dig group `fsc-store-openers` during `Install` (see [DB drivers](../platform/view/services/db-driver.md#reaching-stores-from-node-migrate)).
- The storage fixtures under `platform/fabric/services/db/driver/sql/testdata/` hold databases written by v0.26.0 and v0.27.0, which the tests migrate at every change.

## Fabric API

- New: `endorser.ValidateReceived(ch, tx)` and `endorser.ErrInvalidTransaction`
  (`platform/fabric/services/endorser`), for code that builds a `*fabric.Transaction` from bytes
  outside `endorser.NewTransactionFromBytes` or `endorseView` and wants the same check. It decides
  from the network of `tx` whether to run the txID check.
- New: `security.Rejections`, `security.GetRejections`, and the `security.Kind` constants
  (`platform/view/services/security`), registered in the view SDK. Existing code does not need to
  change; it is used by the new endorser check.

# Checklist

Operators:

- Add `fsc_view_services_security_rejections` to dashboards, and alert if `invalid_tx`
  rises steadily rather than in an isolated burst, which can indicate a misbehaving or malicious
  peer.
- If a transaction a peer builds with `fabric.WithTxID` starts being refused, confirm the peer
  passes a txID equal to `ComputeTxID(nonce, creator)`.
