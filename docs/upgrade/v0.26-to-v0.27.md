# Upgrading from v0.26 to v0.27

This guide takes an application built on Fabric Smart Client (FSC) v0.26.0 to v0.27.0. It has two
parts: [operators](#for-operators) (configuration, storage, network behaviour, monitoring) and
[developers](#for-developers) (Go API). Coming from an older release, first follow
[v0.13-to-v0.26.md](v0.13-to-v0.26.md).

Most changes in v0.27 keep a node running when something it depends on fails, such as its
Postgres database, a peer or orderer, or a remote node in the middle of a protocol. No
configuration key is renamed or removed, and a v0.26 `core.yaml`
starts unchanged. The vault and the KVS reorder their primary key once on first start; there is
no other data migration.

The per-release details are in the
[GitHub release notes](https://github.com/hyperledger-labs/fabric-smart-client/releases).

## Platforms

Every section starts with an **Applies to** line naming one of these scopes:

| Scope | Meaning |
| --- | --- |
| **Every node** | The FSC node itself: views, P2P, the web and gRPC listeners, monitoring, KVS and identity storage. Applies whatever network the node connects to. |
| **Fabric and Fabric-x** | The Fabric driver code and the `fabric.<network>` configuration that both platforms share: network TLS, `peers`, `ordering`, `channels`, the endorser and state services. A Fabric-x deployment cannot skip these. |
| **Fabric only** | Parts that only the Fabric platform uses: the Fabric vault store, block delivery and commit pipeline, discovery, chaincode. |
| **Fabric-x only** | The Fabric-x committer integration: query and notification services, the Fabric-x vault, ledger and finality. |

What to read:

| You run | Read sections marked |
| --- | --- |
| Fabric | Every node, Fabric and Fabric-x, Fabric only |
| Fabric-x | Every node, Fabric and Fabric-x, Fabric-x only |

Mixed tables have a **Platform** column with the same scopes.

## Before you start

| Step | Platform |
| --- | --- |
| Back up every database the node uses (KVS, vault, endpoint bindings). The first start reorders the primary key of the vault state table and of the KVS table. | Every node |
| On Postgres, make sure the database user owns the vault state and KVS tables, or reordering their primary key fails startup (see [Storage](#storage)). | Every node |
| Check the node's environment for variables that start with `CORE` but not `CORE_`; the node no longer reads them (see [Configuration from the environment](#configuration-from-the-environment)). | Every node |
| Upgrade every FSC node that talks to another over P2P in the same window where you can. A v0.26 node does not answer a view it does not host, so its peer keeps waiting until its session times out (see [P2P and sessions](#p2p-and-sessions)). | Every node |

| | v0.26 | v0.27 | Platform |

| Go | 1.27.3 | 1.27.3 | Every node |
| `modernc.org/sqlite` | v1.60.1 | v1.61.0 | Every node |

  the same version; each is tagged separately.

# For operators

## Storage

**Applies to:** Every node, with Fabric-only items marked.

Primary keys:

- Fabric only: the vault state table's primary key becomes `(ns, pkey)`. Every state query
  filters on one namespace, and with `(pkey, ns)` a range scan read the keys of every namespace
  in the range.
- The KVS table gets the same `(ns, pkey)` key, for the same reason.
- Fresh tables are created with the new key. On first start, an existing `(pkey, ns)` key is
  reordered once, on Postgres and SQLite. Replicas that share a database reorder it once between
  them.
- On Postgres the key is dropped and added back under `ACCESS EXCLUSIVE`, which needs a user that
  owns the table. SQLite rebuilds the table in one transaction; a replica that waits on that
  rebuild past `busy_timeout` fails to start with `SQLITE_BUSY` and finds the table reordered on
  restart.
- Any other key order, or a table without a primary key, fails startup and leaves the table
  unchanged.
- An older node keeps working against a reordered table.

Postgres:

- A node waits for Postgres at startup. `postgres.Open` retries the connection with backoff for
  `startupConnectTimeout` (persistence `opts`, default `60s`; `0` or negative selects the
  default), each attempt bounded by 5s. A node started together with its database no longer
  exits.
- A lost connection is retried instead of failing: SQLSTATE `08xxx`, `57P01`, `57P02`, `57P03` and `53300`
  (`too_many_connections`), an expired `connect_timeout`, closed connections, network errors and
  EOF. A rejected password or a missing database is still an error (see
  [Fabric](#fabric) for what the committer does with it).
- With the `tls` block enabled, every host of a multi-host `dataSource` is tried, in order, each
  with the attempts its `ssl_mode` requires. Before, only the first host was used, so
  `postgres://u:p@pg-a:5432,pg-b:5432/db?target_session_attrs=read-write` could not fail over.
- Fabric only: the vault rejects the isolation levels `LevelWriteCommitted` and
  `LevelLinearizable`, which Postgres does not have, with an FSC error before it opens a
  transaction, instead of a pgx error from `BeginTx`.

SQLite:

- The default pragmas (`busy_timeout(5000)`, `journal_mode(WAL)`, `synchronous(NORMAL)`,
  `temp_store(memory)`, `foreign_keys(ON)`) are applied to every connection in both pools. Before,
  they reached only one pooled connection, so the other readers ran with `busy_timeout=0` and
  failed with `SQLITE_BUSY` at once.
- A pragma the `dataSource` already sets, as `_pragma=name(...)` or a driver shorthand such as
  `_busy_timeout`, is not overridden.
- The `cache_size=1000000000` default is dropped, since as a per-connection setting it let
  page-cache memory grow with every read connection. Set it in the `dataSource` if you rely on it.
- A write that keeps failing with `SQLITE_BUSY` is retried 3 times and then returns the error,
  instead of retrying forever.

Persistence names:

- A store key that names a persistence (`fsc.kvs.persistence`,
  `fabric.<network>.vault.persistence`, ...) accepts only letters, digits, `_` and `-`. A name with
  `.` or spaces, or a `dataSource` written where a name is expected, fails startup with an error
  that names the key but not the value, so a password in a misplaced `dataSource` does not reach
  the log.

## Configuration from the environment

**Applies to:** Every node.

- Only variables that start with `CORE_` are read. A variable such as `COREPACK_ENABLE_AUTO_PIN`
  used to become the key `corepack.enable.auto.pin`.
- `__` in a variable name stands for a literal `_` in the key; a single `_` still separates two
  levels. This reaches keys that contain an underscore, which no variable could set before:
  `CORE_FSC_PERSISTENCES_TOKEN__PERSISTENCE_OPTS_DATASOURCE` sets
  `fsc.persistences.token_persistence.opts.dataSource`, and
  `CORE_FSC_PERSISTENCES_DEFAULT_OPTS_TLS_SSL__MODE` sets the Postgres `tls.ssl_mode`. No
  existing variable changes meaning unless it contains `__`.

## View API and `version`

**Applies to:** Every node.

- The HTTP binding of the view API, its HTTP client and the WebSocket stream route ignore JSON
  fields they do not know, as gRPC already does. A node and its clients keep working across
  versions when a view-API message gains a field.
- `version` also prints the FSC version, the application module and its version, and the VCS
  revision (see [`version`](../reference/node-cli.md#version)). Scripts that parse its output
  must allow the extra lines.

## Shutdown

**Applies to:** Every node.

On SIGTERM, SIGINT or `Node.Stop` the node drains before it stops (see
[shutdown.md](../platform/view/services/shutdown.md)):

- `Node.Stop` and `node start` block for up to `fsc.shutdown.drainTimeout` plus
  `fsc.shutdown.teardownTimeout`, 30s each by default. A v0.26 node returned at once. Set
  Kubernetes `terminationGracePeriodSeconds` to at least the `preStop` sleep plus both timeouts
  plus 5s (70s with a 5s `preStop` and the defaults).
- `/readyz` answers 503 with `{"status":"not ready","reason":"draining"}` while the node drains;
  `/healthz` stays 200.
- A new view-API command gets gRPC `Unavailable` (HTTP 503, WebSocket close 1013): retry it on
  another replica. A view the shutdown cancelled at the drain deadline gets gRPC `Aborted`
  (HTTP 409): it may have had effects, so check its outcome instead of retrying it. Clients that
  read only `CommandResponse.err` see the `Aborted` case as a call error.
- A new P2P protocol gets the error `draining: node is draining`; protocols in progress finish.
- The `fsc.grpc` listener always serves the gRPC health service and reports `NOT_SERVING` while
  the node drains.

## P2P and sessions

**Applies to:** Every node.

Unknown views and rejections:

- Calling a view that the other node has no responder for fails at once with
  `unknown_view: <view>`, where `<view>` is the initiator view's identifier, for example
  `unknown_view: github.com/acme/app/views/Transfer`. This usually means the two nodes run
  different versions of the application, or the view moved to another package. A v0.26 node
  only logs `No responder exists`, and the initiator waits until its session times out.
- A node whose peer already runs `fsc.p2p.maxRespondersPerPeer` responders answers with
  `busy: too many concurrent responders for this peer`. Code that matched the payload
  `too many concurrent responders for this peer` exactly must match the `busy: ` prefix or a
  substring instead.
- A first P2P message with status `ERROR` or no caller view is dropped. It neither starts a
  responder nor gets a reply, so two nodes cannot answer each other's rejections.
- A rejection is sent only on a stream to the peer that already exists; the node never opens a
  connection to send one.

Sessions:

- A session whose streams all died closes on its own after a 5-second grace period, unless a new
  stream attaches in the meantime. A view waiting on `Receive()` after its counterparty crashed
  gets a closed channel instead of waiting for its own timer or forever. On libp2p all sessions to
  a peer share one stream, so a dead stream closes every session to that peer that neither sends
  nor receives within the grace period.
- A closed session leaves the session registry. Messages for a session that closed on its own are
  dropped for a minute, so a late message does not start a new responder for a finished protocol.
- Endorsement collection fails with an error when the session to an endorser closes while it waits.

## Fabric and Fabric-x endpoints

**Applies to:** Fabric and Fabric-x, with Fabric-x-only items marked.

- A peer or orderer that just failed is skipped for 30 seconds when the node picks one to connect
  to. If every candidate failed recently, any of them may be picked.
- Fabric-x only: the query and notification services accept several committer endpoints. The node
  keeps a connection to each for its lifetime and uses the first one, in configuration order, that
  is not failing. The notification stream picks an endpoint on every reconnect, and the query
  service on every request, retrying once on another endpoint when a call fails with
  `Unavailable`. An endpoint that is down at startup no longer delays startup, and
  `connectionTimeout` has no effect on these endpoints.

## Fabric

**Applies to:** Fabric only.

Committer and replicas:

- A block whose commit fails with a lost database connection is retried until it commits or the
  delivery stops, with exponential backoff and full jitter (first delay at most
  `committer.retrySleep`, at most one minute). These attempts do not count against
  `committer.retries`, so a Postgres outage longer than `retries × retrySleep` no longer stops the
  channel's block delivery. Contention (`SqlBusy`, deadlocks) keeps the bounded budget. Every retry
  of either kind increments `commit_retries`.
- A transaction that Fabric marks invalid reaches Invalid in the vault even when the vault fails
  while recording it.
- A transaction that this node discarded locally but that Fabric's block marks valid, such as a
  stale Busy one, is committed with the block's read-write set.
- Replicas that share a vault each apply every config block, including those another replica
  recorded, and a restarting replica catches up on config blocks committed while it was down.
- A node that crashed while committing a config block starts, and delivery replays that block.

Finality:

- `IsFinal` waits `CommitterFinalityUnknownTXTimeout` between retries of a Busy transaction. When
  its listening window runs out, the error wraps `driver.ErrFinalityTimeout` and names the last
  status read, for example `last known status [busy]`. A cancelled or expired caller context is
  returned as `ctx.Err()`.

## Fabric-x

**Applies to:** Fabric-x only.

- The notification stream and the query service report their connection state as the
  `fabricx_notification` and `fabricx_query` components (see [Monitoring](#monitoring)). The
  `fabricx_query` series appears after the first answered query, so a query service that was never
  reached does not hold `/readyz` at 503.

## Monitoring

**Applies to:** Every node, with platform-specific items marked.

| Change | Platform |
| --- | --- |
| New: `fsc_shutdown_draining` is 1 while the node drains before it stops. | Every node |
| New: `fsc_view_services_view_p2p_rejections{reason}` counts P2P rejections by `reason` (`busy`, `unknown_view`, `draining`). A rising `unknown_view` rate usually means the nodes run different application versions. | Every node |
| The metrics catalog lists the gRPC connection counters under the name the code exports, `fsc_common_services_grpc_conn_opened` and `_closed` (it listed them as `fsc_view_services_grpc_conn_*`). The default runtime does not export them. | Every node |
| The connection state component `database_notifier` is removed; it reported nothing. | Every node |
| Removed: `fsc_view_services_tracing_listens_operations` and `fsc_view_services_tracing_listens_duration`. They always read 0. | Fabric only |
| `commit_retries` also counts retries after a lost database connection, which no longer count toward `commit_failures`. During a long Postgres outage, alert on a rising `commit_retries` together with the database connection state rather than on `commit_failures`. | Fabric only |
| `fsc_fabric_core_generic_ordering_ordered_transactions` counts transactions on BFT networks as well. It read 0 there before. | Fabric and Fabric-x |
| New connection state components `fabricx_notification` and `fabricx_query`, labelled by network, channel and endpoint. | Fabric-x only |

# For developers

Most changes below are compile errors. Behaviour-only changes are called out.

## Views, sessions and communication

**Applies to:** Every node.

- `DeleteSession` is removed from `P2PNode`, `comm.Service`, `view.SessionFactory` and
  `p2p.CommLayer`; a view context closes the session instances it holds.
  `Sessions.GetSessionInfos` is replaced by `Sessions.All`.
- `Context.GetSessionByID` replaces a cached session that has closed instead of returning it.
- `p2p.NewService` takes optional `...p2p.Option` arguments, such as `p2p.WithMetrics`. Existing
  callers compile unchanged.
- Behaviour: `Node.Stop` calls `Stop()` on every SDK in reverse install order after it cancels the
  node context. An SDK that stopped components in a `ctx.Done()` goroutine should do it in
  `Stop()` and call the wrapped SDK's `Stop()` last; the Fabric SDK now does. The drain finds the
  view manager as a `node.Drainer` in the registry, so wrapper SDKs pass nothing through.
- Behaviour: `CommLayer.ReplyError` writes only to a stream that already exists and returns an
  error when there is none; it never opens a connection. Its payload goes out with an empty
  caller.

## Storage

**Applies to:** Every node, with Fabric-only items marked.

- `postgres.Notifier`, `NewNotifier`, `AllOperations`, `NewSimplePrimaryKey`, `NewBytePrimaryKey`
  and `KeyValueStoreNotifier` are removed from
  `platform/view/services/storage/driver/sql/postgres`, and `connstate.ComponentDatabaseNotifier`
  from `platform/view/services/metrics/connstate`. FSC never constructed them.
- `postgres.NewKeyValueStore` returns `*postgres.KeyValueStore`. Code that type-asserts the store
  to `*common.KeyValueStore` must use its `KeyValueStore` field.
- `driver.ErrConnectionLost` is a new sentinel for a broken or unopenable database connection.
  The Postgres error mapper returns it, and `SqlBusy` also covers SQLSTATE `40001` and SQLite's
  extended busy codes.
- `NewWrappedIterator` passes row-read errors through a `driver.SQLErrorWrapper`. The SQL
  iterators return `rows.Err()` when reading rows fails, so a truncated result is an error.
- `driver.EnvelopeService.Exists` returns `(bool, error)`. Implementations must return the store's
  error.
- Behaviour: `kvs.GetExisting` no longer caches empty values.

## Fabric and Fabric-x API

**Applies to:** Fabric and Fabric-x, with Fabric-x-only items marked.

- `driver.ConfigService` has a new method `ReportFailure(address string)`. External
  implementations and hand-written fakes must add it; regenerate counterfeiter mocks.
- `driver.ErrFinalityTimeout` is a new sentinel for a finality wait that ran out (see
  [Fabric](#fabric)).
- Fabric-x only: `queryservice.NewProvider` and `finality.NewListenerManagerProvider` take a
  `*connstate.Metrics`. `queryservice.NewRemoteQueryService` takes a client factory
  `func() (committerpb.QueryServiceClient, string, error)` instead of a fixed client, and a tracker
  func; pass `nil` to report nothing.

## Integration test harness (`nwo`)

**Applies to:** Every node.

- `web/client.Config`, `NewClient` and `Client.Metrics` are removed from
  `platform/view/services/web/client`. Read node metrics with
  `integration/nwo/client.MetricsClient`. `NewWebClientConfigFromFSC` is replaced by
  `NewWebConnectionConfigFromFSC`, which returns a `grpc.ConnectionConfig`.
- `Topology.SetP2PMessageSizeLimits` sets `fsc.p2p.maxRecvMsgSize` and `maxSendMsgSize` on every
  FSC node.
- The web client gains `Ready`, which probes `GET /readyz`.

# Checklist

Operators:

| Step | Platform |
| --- | --- |
| Back up databases. | Every node |
| On Postgres, check that the database user owns the vault state and KVS tables. | Every node |
| Check that no variable you rely on starts with `CORE` but not `CORE_`. To set a key that contains `_` from the environment, write it as `__`. | Every node |
| Check that every persistence name contains only letters, digits, `_` and `-`. | Every node |
| Set `cache_size` in the SQLite `dataSource` if you relied on the old default. | Every node |
| Optionally set `startupConnectTimeout` for Postgres persistences. | Every node |
| Upgrade P2P peers in the same window; update code that matched the old busy payload. | Every node |
| Set `fsc.shutdown.drainTimeout` to at least your longest view and raise `terminationGracePeriodSeconds` to match. | Every node |
| Update scripts that parse the output of `version`. | Every node |
| Add `fsc_view_services_view_p2p_rejections` to dashboards; drop the `listens` tracer families and `database_notifier`. | Every node |
| Alert on `commit_retries` together with the database connection state during Postgres outages. | Fabric only |
| List several committer endpoints if you run more than one; watch `fabricx_notification` and `fabricx_query`. | Fabric-x only |
| Start one node in staging against a copy of production data and check that the primary keys reorder. | Every node |

Developers:

1. Bump every FSC module you use to v0.27.0.
2. Replace `DeleteSession` calls and `Sessions.GetSessionInfos`.
3. Add `ReportFailure` to `driver.ConfigService` implementations; return an error from
   `EnvelopeService.Exists`; regenerate mocks.
4. Remove uses of the Postgres notifier and of `connstate.ComponentDatabaseNotifier`.
5. Fabric-x: update `queryservice.NewProvider`, `NewRemoteQueryService` and
   `finality.NewListenerManagerProvider` callers.
6. Integration tests: move metric reads to `nwo/client.MetricsClient`.
7. Run the unit and integration tests.
